# Retained candidate experiment (isolated)

This is an unintegrated development prototype. It is not imported by the scanner, replay runner, or production UI, and it must not be treated as a scanner performance or recognition improvement.

The prototype tests budgeting for a candidate's image and preview using an 8 MiB maximum estimate of RGBA pixel bytes. This estimate excludes browser, GPU, canvas, and object overhead. It preserves the original source and capture order metadata, clears inferred identity/field targets, and declines full, invalid or obviously shared ownership. Reservations reject a canvas shared between two reservations even if used as an image in one and a preview in the other. The handoff also checks cross-role aliases against its two supplied retry arrays. Those checks alone do not cover the main queue, active readers, or asynchronous preview encoders, and do not prove all ownership is unique or release is safe.

An attempted opt-in scanner connection was removed. A retry lane does not establish capture-order execution: a newer main-queue item can be read before the retained older item. Its source order metadata may support freshness decisions, but is not proof of chronological reading. Furthermore, admitting a candidate into a second queue while the first queue's replacement callback can still throw is not an atomic ownership transfer. Diagnostic callbacks or cancellation/errors at this boundary can leave duplicate owners or lose evidence. The removed connection included the debug flag, display metrics, budget hooks, and queue replacement handoff. Existing scanner and replay behavior is not intentionally changed.

Before any integration, design a single-owner, transactional handoff that has explicit rollback or commit, verifies ownership across all live lanes, accounts for asynchronous consumers, and produces a visible unresolved/lost-input state on every failure. Specify and test actual processing order separately from capture-order evidence; bound all retained data; cover cancellation, errors, retry, saturation, and shared resources; validate with replay and real input. Only measured, regression-checked behavior may be considered for default use.

The tests exercise isolated budget and conflict checks. They do not test scanner integration, full ownership transfer, actual memory, UI latency, recognition accuracy, or replay equivalence.
