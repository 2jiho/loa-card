# 입력 기록과 재현 설계

스캐너 변경을 실제 입력으로 검증하기 위한 기록·재현·비교의 계약이다. 스캔 자체의 흐름은 [스캐너 구조](scanner-pipeline.md), 명령은 [개발과 검증](development.md)을 따른다. v0.3.0 이전의 앱 진단 기록(`.loareplay`)과 프레임 단위 루프의 재현 구조는 제거됐으며 Git 이력에 남아 있다.

## 원칙

- 새 실데이터는 비공개 로컬 사례로 **누적**한다. 새 입력이 이전 입력을 덮어쓰지 않는다. 입력 순서·시각·무결성(SHA-256)·당시 코드 버전을 보존한다.
- 세 가지 검증을 구분한다.
  1. **같은 입력 재판독**: 기록한 프레임을 현재 코드로 다시 읽는다(카드 값·확정 수 비교).
  2. **상태 갱신 재생**: 같은 실행에서 화면이 보여 준 상태의 흐름을 남겨 검사한다(진행 창 기록).
  3. **실시간 성능**: 원래 속도로 프레임을 보내며 공유 종료 시점의 결과, 최종 결과, 처리 프레임 수를 잰다.
- 라이브와 재현은 같은 판독·상태 갱신 경로(`runScanner` → 줄 중심 스캔)를 쓴다. 재현 전용 판독 경로를 따로 두지 않는다.
- 프로그램이 낸 결과(baseline)를 사람이 확인한 정답(expected)으로 자동 승격하지 않는다. 입력이나 기록이 없는 문제를 완전히 재현했다고 보고하지 않는다.

## 기록

개발 서버(`npm run dev`)에서 앱으로 화면을 공유하면 `orchestration/scanner.ts`가 공유를 로컬 서버에 기록한다(`reproduction/share-recorder.ts` → `dev/recording-server.ts`).

- 위치: `fixtures/local/recordings/<id>/`(Git·배포 제외). `frames.mkv`(무손실 H.264), `frames.jsonl`(프레임별 순번·미디어 시각·전달 시각), `meta.json`(크기·픽셀 형식·프레임 수·완전성·SHA-256·브라우저·코드 버전).
- 범위: 카드 창이 보인 구간만 남긴다. `?record=all`이면 공유 전체를 남기고, 기록한 적 없는 배율의 화면이거나 처음 5초 동안 창을 찾지 못하면 저절로 전체를 남긴다.
- 기록은 스캔을 기다리게 하지 않는다. 기록이 실패하거나 누락돼도 스캔은 계속되며, 탭 제목과 meta의 note에 남는다.
- 공유 중 앱의 실제 결과도 같은 기록 옆에 `run-live.json`으로 남긴다(`reproduction/live-run-report.ts`).
- 파생 기록(`scripts/derive-recording.mjs`)은 기존 기록의 프레임을 다른 순서로 이어 붙인 것이다(아래에서 위로, 중간에서 시작). 실제로 그렇게 공유한 기록이 아니며 meta의 note에 출처가 남는다.

## 재현

`node scripts/run-recording-replay.mjs --id <id> --mode <방식>`이 헤드리스 브라우저로 `/dev/recording.html`을 열어 실행하고 보고서를 `runs/`에 남긴다.

| 방식 | 경로 | 남기는 것 |
|---|---|---|
| `realtime` | 앱과 같은 `runScanner` | 카드 값, 상태 문구, 전달 지연, 1초 간격 진행 |
| `rowlive` | 줄 중심 스캔 직접 | 카드 값과 확정 여부, 프레임·판독 측정, 진행 창 상태 기록(`monitorTimeline`) |
| `rowread`·`rowlight`·`rows`·`lean`·`artfail`·`gridfit`·`cardmap` | 측정 도구 | 스캔 결과가 아님 |

프레임은 기록된 전달 시각대로 보낸다. 처리 속도는 이 PC의 부하를 따르므로 같은 기록도 실행마다 처리 프레임 수와 공유 종료 시점의 결과가 다를 수 있다. 결정적인 순차 재판독은 이전 루프와 함께 제거됐다. 비교는 같은 기록을 여러 번 실행해 공유 종료 시점과 최종 결과를 따로 본다.

## 검사

- 카드 값: 보고서의 `cards`(이름·각성·장수·확정)를 고정한 기준 실행이나 다른 빌드의 실행과 비교한다(`scripts/run-regression.mjs`, `scripts/compare-recording-runs.mjs`). 보고서의 입력 SHA-256이 같은 실행끼리만 비교한다. 같다는 것은 기준과 같다는 뜻이지 정답이라는 뜻이 아니다.
- 진행 창: `scripts/check-monitor-timeline.mjs`가 지도 지연·깜빡임·되돌아감·안내 흔들림·종료 상태와 결과의 일치, 카드별 화면 사진을 검사한다. `/dev/monitor-timeline.html`은 같은 기록을 실제 진행 창 컴포넌트로 다시 그려 배치 변화와 넘침을 잰다.
- 사람이 확인한 정답은 코퍼스의 사람 확인 라벨로 따로 둔다(`npm run corpus -- import-human` 등). 코퍼스에서 가져온 기록의 실행은 `scripts/compare-labels.mjs`로 라벨과 비교한다. 부분 라벨의 통과를 전체 인식률로 해석하지 않는다.
- 회귀 묶음: 역할이 다른 기록의 목록은 비공개 `fixtures/local/regression-set.json`에 두고 `scripts/run-regression.mjs`로 위 검사를 한 번에 돌린다([화면 공유 기록](dev-recording.md#회귀-묶음)).

## 코퍼스

사용자가 제공한 영상·사진은 `npm run corpus -- add`로 `fixtures/local/corpus/`에 순서와 해시를 보존해 등록한다. 지금 스캐너로 실행하려면 `scripts/import-video-recording.mjs`로 기록 형식으로 바꾼다. 영상은 프레임을 무손실로 옮겨 원래 시각대로, 스크린샷은 한 장씩 1초 멈춘 화면으로 재생한다. 이렇게 만든 기록은 개발 서버가 기록한 공유가 아니며 meta에 원본과 사례가 남는다. 이전 버전의 진단 파일(`.loareplay`, `.loaraw`)은 보관·검증만 할 수 있고 다시 실행하는 경로는 없다.

## 개발 순서

사례 등록(기록) → 수정 전 결과 → 원인 재현 → 수정 → 회귀 묶음 재실행(카드 값·진행 창·라벨 점검) → 실제 공유로 재현할 수 없는 부분(손 움직임, 게임 부하)만 사용자 확인. 측정 항목은 정확성, 화면 반응 지연, 판독 지연, 처리 프레임 수, 메모리, 기록 용량이다.

## 한계

- 기록은 개발 서버에서만 남는다. 배포 페이지에는 진단 기록 기능이 없다.
- 기록은 카드 창이 보인 구간만 남기는 것이 기본이라, 창을 찾지 못한 프레임의 원인은 `?record=all`로 남긴 기록에서만 볼 수 있다.
- 재실행은 이 PC의 처리 속도를 따른다. 다른 장치·브라우저·게임 부하는 재현하지 않는다.
