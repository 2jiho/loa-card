# 개발과 검증

## 재현 가능한 기본 환경

Node.js 22, npm, Git을 사용한다. `npm ci`는 lockfile의 버전을 설치한다. `.env`, 서비스 키, 게임 설치는 필요 없다. Python과 로컬 게임 DB는 선택적인 데이터 재생성에만 필요하다.

```sh
npm ci
npm run lint
npm test
npm run build
npm run preview
```

`predev`/`prebuild`가 라이선스 고지와 OCR 자산을 준비한다. OpenCV 실행 파일도 설치된 npm 패키지에서 `public/ocr/opencv.js`로 복사하므로 준비 단계를 생략한 직접 Vite 실행은 피한다. 최초 준비는 GitHub/Hugging Face 공개 모델 다운로드를 사용하고 고정된 리비전·SHA-256을 확인한다. `work/ocr`, `work/paddle`, `work/paddle-v6` 캐시와 `public/ocr`는 삭제 후 다시 만들 수 있다. 네트워크 차단이나 해시 불일치는 준비 오류이며 무결성 검사를 끄지 않는다.

코드·테스트는 OS 독립적인 상대 경로를 사용한다. 테스트는 `tests/*.test.ts`, 최소 회귀 입력은 `tests/fixtures/`에 있다. 실제 영상/전체 화면은 없어도 실행된다. CI의 Check와 Pages 배포도 lint → test → build 순서다.

## 브라우저에서 영상·이미지 검사

1. `npm run dev` 후 표시된 주소의 `/dev/scanner.html`을 연다.
2. 등록한 사례를 선택하거나 영상 하나·이미지 묶음을 직접 선택한다. 이미지는 등록 목록 또는 파일 선택 목록의 순서를 유지한다.
3. **획득만 검사**를 선택하면 OCR 없이 검출·크롭 제외 사유를 확인한다. 전체 판독은 선택을 해제한다.
4. 등록한 사례는 실행 종료 후 상태·진단을 해당 사례의 `runs/`에 자동 기록한다. 저장 실패 시 **로컬 기록 다시 저장**으로 재시도한다. **결과 JSON 저장**은 같은 보고서를 별도로 내려받는다. 직접 선택한 파일은 이 버튼으로 보관한다. 일반 앱의 목록·백업과 별개이며 시작 목록은 항상 비어 있다.
5. 수정 전후 같은 입력을 비교한다. 원본과 JSON에는 사용자 화면이 포함될 수 있으므로 공개 이슈에 그대로 올리지 않는다.

### 여러 원본의 회귀 비교

같은 페이지의 **원본 일괄 비교**에서 사례를 최대 16개 선택하고 비교할 판독을 고른다. 회색조 이름 보완·미세 위치 보정·대비 이름 보완 중 하나를 기본 방식과 비교한다. 대비 보완은 매 실행에 명시적으로 켜거나 끄며, 준비·판독·보고서에 같은 이름 판독 설정을 전달한다. 재현 파일은 기록된 설정을 우선한다. 등록 목록 순서와 각 사례 내부의 원본 순서를 유지하고, 매 실행은 빈 목록과 새 판독기를 사용한다. 선행 실행의 판독·정리·개별 보고서 저장이 끝난 뒤에만 다음 실행을 시작한다. 다른 입력 실험과 함께 실행하지 않는다.

개별 보고서는 기존 `runs/`에 불변 파일로 보관한다. 일괄 요약은 파일 참조·소스 digest·수량·확인 건수와 이름/각성/장수의 정규 해시만 담으며 이미지·전체 사건을 복제하지 않는다. 최대 32회·요약 256KiB다. 저장 실패, 코드 변경, 실행 오류와 중지는 부분 결과를 남기고 다음 실행을 막는다. 이름·필드 미확정이나 수량 불일치는 해당 결과에 남기고 다른 원본 검사를 계속한다.

워치독의 제한 시간 반환과 실제 내부 작업 종료는 구분한다. 취소·정체 후 내부 작업이 남아 있으면 새 검사를 잠그고, 작업 종료 알림을 받은 뒤 해제한다. 결과·요약 저장은 사용할 수 있다. 종료 알림은 내부 Promise의 정착을 뜻하며 브라우저·OS의 모든 네이티브 메모리 회수를 보증하지 않는다. 종료되지 않는 경우 개발 페이지를 새로고침해 격리한다.

**일괄 실행 완료**와 판독·회귀 통과는 구분한다. `clean`은 표시 수량과 확인 항목의 프로그램 검사이며 사람 정답이 아니다. 요약 버전 2의 `variant`와 `variantIndex`는 기본 방식과 비교한 실험 및 실행 인덱스를 나타낸다. `cardFieldsEqual`은 같은 사례·모드·소스의 기본/선택 판독 카드 값 비교다. 실험끼리는 비교하지 않는다. 값이 달라지면 양쪽 개별 보고서와 독립 라벨을 확인한다. 이 일괄 경로는 전체 프레임 순차 검사이므로 처리 시간을 화면 공유 지연으로 해석하지 않는다. 입력 무결성은 실행 전에 `npm run corpus -- verify`로 별도 확인한다.

`elapsedKind`는 입력 로드·엔진 준비를 포함한다. `offline-preparation-and-processing`과 `live-preparation-playback-and-drain`을 구분하며, 소스 해시 계산·개별 기록 저장은 `elapsedMs` 밖이다. 서로 다른 시간 경계의 수치를 직접 비교하지 않는다.

`validation.visibility`는 표시 상태 변경 시각을 같은 페이지의 `performance.now()`로 최대 64건 보관한다. 누락·잘못된 시계·관측 실패를 별도 집계하며, 누락된 변경의 시각을 추정하지 않는다. `performance.clockOrigin`은 해시 검사 뒤 실행 시작, 입력·판독 사건의 상대 시각 기준, 제한 시간이 적용된 실행 반환 시각을 연결한다. 반환 시각은 모든 내부·OS 자원의 회수 시각을 뜻하지 않는다. 진단 저장 중의 탭 변경과 판독 중의 변경을 구분할 수 있지만, 변경과 지연의 인과관계를 증명하지는 않는다. `scanner-clock` 이후 실행 사건의 상대 시각과 원본 영상 PTS·사진의 합성 시각 0은 서로 다른 도메인이다.

`runReturnedAtMs`는 스캐너 호출 직후가 아니라 호출자 측의 알려진 정리까지 포함한 기존 측정 구간의 끝이다. 스캐너 판독 사건에는 `scannerTraceOriginMs`, DEV의 `source-playback`에는 `runStartedAtMs`를 사용한다. 같은 스트림에 섞인 모든 사건에 한 기준을 적용하지 않는다. 특히 출처가 없는 `media-recording-error`는 두 경로에서 올 수 있으므로 기준 시각을 추정하지 않는다.

이 페이지는 빈 목록에서 **전체 프레임 순차 검사**와 **영상 1배속 · 실시간 처리 경로**를 선택한다. 순차 검사는 영상 디코드 프레임을 순서대로 읽는다. 1배속 검사는 모델 준비 후 0초부터 네이티브 captureStream으로 `screen` 수집·병렬 판독 경로를 실행한다. 사진은 순차 검사만 지원한다. OS 화면 공유 권한·장치의 프레임 도착·메인 앱 렌더링 지연 검사는 실제 게임 창을 선택하여 별도로 확인한다. Dev 페이지는 프로덕션 엔트리에 포함하지 않는다.

검사 중에는 실제 앱의 진행창 컴포넌트와 외부 store를 재사용하는 미리보기도 갱신한다. 따라서 위치 미연결 상태의 최근 40칸과 판독 대기·판독 중·완료 표시를 같은 입력으로 확인할 수 있다. 보고서의 `ui`·실행 설정·탭 가시성을 함께 비교하며, 진행창 미리보기를 추가하기 전 수치와 동일한 UI 부하라고 가정하지 않는다.

`verify-scan.mjs`, `verify-screenshot-scan.mjs`의 라벨은 초기 특정 영상/사진에 대응한다. 새로 찍은 재고에 적용해 실패를 인식 오류로 단정하지 않는다. 검증용 정답은 입력 촬영 시점과 함께 별도로 작성한다.

## 입력 코퍼스

새로 제공받는 영상·사진·`.loareplay`는 원본을 바꾸지 않고 등록한다. 기본 저장 위치는 Git과 배포에서 제외한 `fixtures/local/corpus/`다. 입력 종류와 **파일 내용·순서·반복**으로 사례를 식별하므로 이름을 바꾼 같은 입력은 중복 저장하지 않는다.

```sh
npm run corpus -- add path/to/recording.mp4 --name fast-scroll --kind video
npm run corpus -- add path/to/first.png path/to/second.png --name screenshots --kind images
npm run corpus -- add path/to/session.loareplay --kind replay
npm run corpus -- list
npm run corpus -- verify
npm run corpus -- compare work/reference.json work/actual.json
npm run corpus -- compare work/partial-reference.json work/actual.json --scope partial
npm run corpus -- replay-state work/actual.json
npm run corpus -- record-run <case-id> work/actual.json
```

사진은 명령에 준 순서를 유지한다. 같은 사진을 여러 번 전달해도 제거하지 않는다. 사례의 `input/` 파일은 읽기 전용으로 사용한다. `verify`는 원본 바이트·순서의 무결성 검사이며 카드 인식 정확도 검사가 아니다. 등록 시 촬영 시각·완전성·baseline·정답은 미확인으로 남긴다.

`compare`는 재현 결과 또는 진단 JSON의 `result`를 읽고 카드 추가·누락·이름·각성·장수·확인 사유, 보관함 수량·판독 수·미식별 수·경험치를 비교한다. `null`은 0과 다르다. 전체 비교는 모든 필드, 부분 비교는 기준에 있는 카드만 검사하며 나머지 차이도 보고서에 남긴다. 일치하면 종료 코드 0, 차이가 있으면 2, 잘못된 파일이면 1이다. 기준과 같다는 뜻이며 기준이 정답이라는 뜻은 아니다. 기대값과 baseline을 자동 생성·교체하지 않는다.

사람이 확인한 일부 카드만 정답으로 쓸 때는 별도 human label 명령을 사용한다. `loacard-human-label` 버전 1은 사례 ID·순서 있는 입력 SHA/크기·확인 문맥과 답변·확인한 카드 필드를 기록한다. `fields`의 생략은 미제공, `{status:'unknown'}`은 명시적 미확인, `{status:'known',value:0}`은 확인한 0이다. 장수·각성 범위와 조합 상한을 검사하며 확인하지 않은 헤더·review·다른 카드를 빈 값으로 채우지 않는다.

```sh
npm run corpus -- import-human <case-id> work/human-label.json --operator-confirmed
npm run corpus -- list-human <case-id>
npm run corpus -- verify-human <label-sha256>
npm run corpus -- compare-human <label-sha256> work/actual.json
```

등록 명령이 반환한 SHA로 라벨을 선택한다. 라벨은 `fixtures/local/corpus/human-labels/`에 내용 해시로 추가하며 기존 사례 manifest·baseline을 고치지 않는다. 실제 크롭 anchor가 있으면 최초 등록에 `--asset work/crop.png`를 명시한다. 이전 개발용 flat sidecar는 `--migrate-private-v1`을 함께 지정할 때만 변환한다. `--operator-confirmed`는 사람이 확인한 자료라는 작업자의 명시적 주장이지 정답의 암호학적 증명이 아니다. 같은 확인 내용에서 만든 원본·재현 라벨은 확인 SHA를 공유하며 독립 확인 두 건으로 세지 않는다.

AI 비전 모델이 프레임을 판독할 때는 카탈로그 이름 목록(`work/catalog-names.txt`)을 먼저 제공해 목록 안에서만 고르게 한다. 후보 압축은 `node dev/vision-catalog-resolve.mjs public/scanner/cards.json work/vision-hypotheses.json`로 한다. 이 결과는 사람 확인 전까지 operator-asserted 초안이며 expected로 자동 승격하지 않는다.

`verify-human`은 입력·라벨·확인 내용·PNG의 해시와 구조를 검사한다. anchor의 전체 RGBA를 다시 복원한 검사와 구분한다. `compare-human`은 해당 사례·입력에 묶인 보고서에서 라벨 필드의 값과 최신 필드 근거를 별도로 검사한다. 이름만 라벨링하면 최신 이름 확정을 검사하고, 숫자를 하나라도 라벨링하면 기존의 유효한 최신 각성·장수쌍 근거도 요구한다. 이때 다른 숫자를 인간 정답으로 추가하지 않는다. 저장된 0장 값이 같아도 최신 관측의 장수가 `null`이면 숫자 검증을 통과하지 않는다. 엄격한 실행 재생·inventory 체크포인트가 없는 보고서는 최신 근거 미지원이다. 종료 코드는 범위 안 값·최신 근거 일치 0, 값 차이 2, 최신 근거 미확정·미지원 3, 잘못된 입력 1이다. `--values-only`는 값만 진단하며 일치해도 최신 근거 통과로 표시하지 않는다. 부분 라벨 통과를 전체 인식률로 해석하지 않는다.

`npm run dev`의 `/dev/scanner.html`에서 **등록한 입력**을 선택하면 사례의 순서를 그대로 실행한다. 영상은 Range 요청으로 읽고, 사진은 한 장씩 열고 해제한다. 자동 기록과 **결과 JSON 저장**은 `caseId`, 입력 해시, 실행 조건·코드 구성과 정규 `result`를 보존한다. 자동 기록은 모든 판독과 소스 확인 후 별도 단계에서 수행하며 스캔 처리 시간에 합산하지 않는다. 10초 안에 저장되지 않으면 실패를 표시하고 기존 스캔 결과와 보고서는 재시도할 수 있게 유지한다. 이 페이지는 원본 해시를 다시 계산하지 않으므로 먼저 `verify`를 실행한다. `.loareplay`는 앱의 스캔 진단에서 사용한다. 개발용 API는 dev 서버에서만 제공하며 공개 빌드에는 포함하지 않는다.

`record-run`도 같은 검증·보관 규칙을 사용한다. 보고서의 사례 ID·입력 순서·해시·크기를 manifest와 대조하고 원본 바이트의 해시를 파일명으로 써 기존 기록을 덮어쓰지 않는다. 같은 바이트는 한 번만 보관한다. 부분·취소·실패 실행도 남기며 수량이나 출처가 불완전한 결과는 구분한다. 모든 run은 프로그램 관측 자료이며 baseline·expected로 자동 승격하지 않는다. POST 보관 API는 실제 loopback·동일 출처의 UTF-8 JSON만 받고 최대 16MiB로 제한한다.

### 검증 기준선 (2026-10-29)

비공개 로컬 코퍼스에서 아래 명령과 결과로 저장 무결성·비교·상태 재생 기준선을 확인했다.

- `npm run corpus -- list` — 사례 목록. 종류·입력 수·바이트 확인.
- `npm run corpus -- verify` — 전체 입력 바이트·순서·해시 일치.
- `npm run corpus -- compare <run1> <run2>` — 같은 사례·모드의 프로그램 관측 비교. `same`은 기준과 같다는 뜻이며 정답 승격이 아니다.
- `npm run corpus -- replay-state <report.json>` — grid·inventory·input·unknownLifecycle·freshness 상태를 기록된 이벤트로 재생해 캡처된 해시와 대조. `input` 채널은 라이브 입력(admission/pipeline)이 기록된 세션에서만 존재하며, 없는 이전 기록은 미지원으로 표시한다.

라이브 1배속 세션(`dev/scanner.html` 자동 세션 저장)의 실측 지표는 보관된 run 보고서에서 분석 도구로 다시 확인한다.

```sh
node --import tsx scripts/analyze-observation-timing.mjs <run.json>
node --import tsx scripts/analyze-input-delivery.mjs <run.json>
```

분석 범위는 읽기 큐 대기·판독 작업 시간, 입력 admission 결정·큐 대기·획득 구간, 프레임 고정 간격·예산, 콜백 간격·Long Task 겹침이다. 이것들은 화면 반영 지연·OCR 정확도·실제 OS 공유 성능을 증명하지 않는다.

`/dev/scanner.html?localpixels=1`은 영상 1배속에서 카드 픽셀 전달만 비교하는 실험이다. 기본 경로는 그대로이며 다른 입력 실험과 함께 실행하지 않는다. 이미 읽은 격자 ROI에서 완전히 포함된 불투명·정수·무배율 140×210 카드만 소유한 픽셀 버퍼로 전달하고, 소수 좌표·축척·잘림·투명·Canvas 보간이 필요한 경우는 기존 경로를 쓴다. `localPixelCrops`는 이 대체 수만 나타낸다. 전체 입력 해시·공통 원본 ID·측정 영수증을 만들지 않는다. 실제 브라우저의 크롭·좌표·특징·품질·이름 영역 일치와 별도 정상 경로 성능 비교를 통과하기 전에는 기본값으로 채택하지 않는다.

보고서에는 기존 앱과 같은 제한된 실패 진단도 포함한다. 원본 프레임 대신 최대 32개·인코딩 문자 합계 1MiB의 크롭을 모으며 실제 판독 PNG를 미리보기보다 우선한다. 필드 진단과 미식별 관측 메타데이터는 각각 1MiB 상한이고, 전체 보고서는 16MiB를 넘으면 저장하지 않는다. `unidentifiedObservations`는 이미지가 빠진 관측도 그룹·캡처 순서·원본 프레임·슬롯·OCR 시도와 함께 남긴다. 이미지 인덱스는 동일 URI로만 연결하고, 없는 이미지는 `null`로 표시한다. 미식별 경고의 전체 발생·퇴역 이력은 아직 이 최종 요약만으로 재생할 수 없다. 진단도 개인 화면이므로 로컬에만 보관하고 공개 이슈에 자동 전송하지 않는다. 입력 API는 실제 소켓의 loopback 연결만 허용한다.

보고서는 프레임 없는 상태 기록도 포함한다. 기록 v2는 128KiB 배치를 비동기 gzip으로 압축한다. 압축 결과 8MiB·총 원문 128MiB·250,000개 이벤트·대기 원문 2MiB 중 한도를 넘으면 부분 기록으로 표시하며, 가져오는 상태 JSON 컨테이너는 최대 12MiB다. **상태 재생 검사** 또는 `replay-state`는 OCR 없이 같은 지도 명령·관측 규칙을 청크별로 실행해 당시 지도·작업 상태 해시와 비교한다. 이벤트 수·청크 수·마지막 순번을 검증하며 누락된 기록은 전체 일치 검사에 사용하지 않는다. 해시가 같아도 위치 판단 자체가 옳거나 실시간 속도가 같다는 뜻은 아니다. 실행 방식과 준비·입력 종료 시각을 함께 기록하므로 순차 검사 시간을 실시간 처리량으로 해석하지 않는다.

새 실행은 목록 시작 상태, 식별 수락·이름·필드 관측과 늦은 정렬 정보도 기록한다. 라이브 입력은 복사 허용·실패·건너뛰기·대기 교체·소유권 해제·실제 획득 프레임 연결을 남긴다. `executionExpected`의 지도·카드 근거·입력 선택 해시를 독립적으로 비교하며 없는 검증점은 미확인으로 남긴다. 같은 선택 사실을 재생하는 것이며 OCR 실행 시간이나 기록되지 않은 입력 픽셀을 복원하는 것은 아니다.

`input-arrival`은 라이브 입력이 admission 경계에 도착했을 때 건너뛰기 판단 전에 남기는 선택적 진단이다. 입력 ID·캡처 시각·세션 경과 도착 시각과, 있는 경우 video callback의 `mediaTime`·`presentedFrames`·`missedFrames` 또는 native `timestamp`(µs)를 분리한다. 서로 다른 시계의 값을 합치거나 callback 카운터를 원본 영상 디코드 순번으로 해석하지 않는다. `input-backup-reservation`은 같은 입력을 store별 백업 예약 ID에 연결한다. 예약만으로 실제 획득 ID·저장 원본과의 연결이나 저장 성공 ACK를 증명하지 않는다. 타입·검증 계약은 [`input-arrival.ts`](../src/features/card-scanner/input-arrival.ts), 기록 파싱은 [`run-state-trace.ts`](../dev/run-state-trace.ts)를 따른다. 두 사건은 상태·admission·완료 판정의 근거가 아니며, 사건이 없는 구버전 기록은 도착 진단 미지원이다.

일반 재생은 전체 이벤트 배열을 보관하지 않는다. 입력 선택은 최대 20,000개, 동시 소유권은 최대 3개이며 한도 초과는 완전 재생을 거부한다. 분석용 `parseRunStateTrace`는 원문 한도까지 모든 이벤트를 객체로 펼치므로 메모리 사용량이 128MiB보다 커질 수 있다. 필요한 경우에만 호출하고 기본 비교에는 `replay-state`를 사용한다.

`performance.monitorPresentation`은 진행창 store 알림부터 React layout commit까지의 지연을 최근 최대 2,048개 표본으로 집계한다. 합쳐진 상태 변경과 아직 반영되지 않은 변경도 구분한다. 캡처부터 화면 표시까지의 전체 지연이나 브라우저의 실제 paint 시간을 측정한 값은 아니다.

개발 빌드의 화면 공유와 dev runner는 별도의 수집·판독 피드백 진단을 연결한다. dev 결과의 `performance.feedbackReceipts`는 실제 대기열 수락 이후, 실제 판독 작업의 시작·종료, 스크롤바 샘플에서 **해당 canonical snapshot의 DOM layout commit**까지를 측정한다. 스크롤·대기·시작·종료 분포는 `byKind`로 구분하며 최근 2,048개 성공 영수증의 공통 창을 나눠 쓴다. 각 단계마다 2,048개를 따로 보관하지 않는다.

현재 측정 대상은 실제 보이는 스크롤 위치 표시와 최근 수집 40칸이다. 관측 출처·처리 프레임·시도는 원래 작업에 남기고, 스크롤 후 표시 프레임·칸은 ScanGrid의 실제 group → work 연결로 별도 전달한다. 원천 칸과 표시 칸이 다르다는 이유로 유효한 연결을 버리거나, 위치가 같다는 이유로 다른 작업을 연결하지 않는다. 실제 DOM의 상태·표시 좌표·레이아웃 가시성이 일치해야 표본이 된다. 출처를 잃은 전체 보관함 투영, 가려진/화면 밖 대상, 렌더링 전에 합쳐진 상태와 동일 값으로 억제된 발행은 별도 계수한다. 표본이 없는 단계는 `null`이며 늦은 이전 시도나 카드 개수로 0ms를 만들지 않는다. 숫자 링과 대기 메타데이터에는 고정 상한이 있고 실제 JS heap·브라우저 전체 메모리와는 구분한다. 상태·알림·자식 렌더를 진단 때문에 추가하지 않는다.

피드백 adapter는 같은 128개·16KiB 메타데이터 예산 안에서 진행 중 시도와 현재 화면에 연결된 작업을 먼저 보존한다. 대기 정보가 퇴역한 뒤 실제 reader가 시작되면, 수락된 Candidate의 정확한 출처와 원래 처리 프레임으로 시작 사실부터 측정한다. 사라진 대기 시각은 복원하지 않는다. 기존 기록 메타데이터를 재사용하며, 다른 진단이 없는 probe 전용 실행만 기존 상한이 있는 Candidate에 프레임 번호 하나를 추가한다. 이 추가 숫자 payload의 명목 상한은 대기열 1,600개 + 재시도 두 큐 각 512개 + 진행 중 작업 수에 각각 8바이트이며, adapter 예산이나 실제 JS 객체·heap 측정에 포함된 값으로 보고하지 않는다. 새로운 원천 메타데이터 저장소나 무제한 큐는 만들지 않는다. 이 장치는 표시 지연을 관찰하는 진단이며 판독 스케줄이나 카드 완료 근거를 바꾸지 않는다.

일반 앱의 개발 빌드는 종료 진입 시점의 피드백 집계를 로컬 진단 `performance.feedbackReceipts`에 최대 8KiB로 복사한다. 캡처 출처·시각·카드·이미지는 이 집계에 포함하지 않으며, 마지막 레이아웃 반영이 나중에 일어나면 그 표본은 빠질 수 있다. 잘못된 집계나 용량 부족은 `feedbackReceiptsUnavailable`로 남기고 기존 카드 결과와 필드 근거를 우선 보존한다. 일반 배포에서는 이 진단을 활성화하지 않는다.

실행 중 lease는 자신의 원래 ObservationWork를 종료할 때까지 보유한다. 더 좋은 크롭이 같은 group을 교체하거나 표시 캐시가 정리되어도 옛 판독의 종료 사실은 원래 출처로 발행하며 새 카드 칸은 바꾸지 않는다. 실제 스캐너의 보유량은 판독 lane 수로 제한된다. 별도 재생에서 종료 없는 start를 계속 주는 경우에는 표시 캐시와 독립적인 2,048개 진행 lease 상한에서 명시적으로 실패한다. 상한 때문에 가짜 종료 사실을 만들거나 현재 카드 완료로 바꾸지 않는다.

이 값은 부분적으로 연결 가능한 대상의 layout commit까지다. 브라우저 paint·창 가림 여부·OS 입력 도착·공유 종료까지의 전체 지연은 증명하지 않는다. PiP는 부모 페이지 clock과 대상의 `ownerDocument`를 사용한다. 표본 개수와 누락·교체·한도 카운터를 함께 확인하고, 이 일부 표본의 p95만으로 전체 실시간 목표 달성을 보고하지 않는다.

실행 전후 현재 소스 해시가 다르면 `source-changed`, 출처 확인에 실패하면 `source-unverified`로 남기고 정상 기준 실행으로 사용하지 않는다. `sourceStart`/`sourceEnd`에는 미추적 코드도 포함된다. `serverStartSignature`는 서버를 켤 때의 값이므로 변경 중인 개발 소스 버전을 대신하지 않는다. 소스 확인 시간과 스캐너 실행 시간은 따로 기록한다.

소스 해시 범위는 보고서의 `scope`를 따른다. 설치된 `node_modules`와 생성한 OCR 모델·WASM의 실제 바이트는 포함하지 않으며 lockfile·고정 해시 선언이 포함된다. 따라서 `sourceChanged:false`만으로 런타임 자산 무결성까지 검증했다고 해석하지 않는다.

새 입력 등록 → 수정 전 결과 → 원인 재현 → 수정 → 이전 사례와 새 사례 재실행을 기본 개발 순서로 사용한다. 공통 입력·상태·기록 전환의 책임과 완료 조건은 [재현 구조 설계](scanner-session-design.md)를 따른다.

## 변경에 따른 확인

- 인식: 정상/잘림/가림/저대비/0장과 최신 관측 충돌을 검사한다. 성능을 위해 확정 조건만 낮추지 않는다.
- 성능: 빈 목록 시작, 입력 길이·해상도·프레임률·장치/브라우저, 첫 결과, 공유 종료 때 확인 수, 최종 확인 수, 누락/추가/필드 차이, 보완 프레임 수를 기록한다.
- 계산: 공유 카드·중간 단계·자원 차감·미확인 입력과 마스터 참조 무결성을 검사한다.
- UI: 밝은/어두운 모드, 데스크톱/좁은 화면, 키보드 탭 이동, 스캔 중 탭 전환, CSV 잘못된 입력과 백업 복원을 확인한다.
- 자산 경로: `/`뿐 아니라 `PAGES_BASE_PATH=/loa-card/`로 빌드해 Worker·WASM·모델·고지 링크가 열리는지 확인한다.

단위 테스트 통과, 전체 영상의 수량 일치, 모든 필드의 수동 정답 일치는 서로 다른 검증이다. 공유 후 보완된 최종 결과를 실시간 결과로 보고하지 않는다.

검사 요약의 `review`는 식별된 카드 중 필드 확인이 필요한 카드 수, `unidentified`는 카드 ID에 연결되지 않은 최종 실패 관측 수다. 같은 카드의 중복 관측일 수 있으므로 두 값을 더해 누락 카드 수로 계산하지 않는다. `unreadable`은 판독 도중 발생한 각성 미판독의 누적 횟수이며 최종 미해결 수가 아니다. 수량 일치만으로 실패 관측을 삭제하지 않는다.

## 진단 API

`runScanner`의 `debug` 인자는 프레임 기록/재현 등 개발 용도다. `debug-bundle.ts`는 LOACARD1 컨테이너 검증, `debug-capture.ts`는 프레임 순회, `debug-store.ts`는 임시 보관을 담당한다. 일반 UI의 입력 재현은 `scan-reproduction.ts`, `reproduction-session-store.ts`, `ScanReplayDialog.tsx`를 사용한다. 기본 자동 기록을 세션별로 보관하며, 저장 실패·한도 초과·중단은 부분 기록으로 남긴다. 진단 화면에서 입력 보관을 끌 수 있으며 작은 진단 요약은 계속 남긴다. 개인 `work/*.html`에 의존하지 않는다.

dev runner의 **자동 세션 저장도 검사**는 `loacard-reproduction-dev`라는 별도 브라우저 DB에 동일 저장 경로를 실행한다. 결과의 `sessionEvidence`는 입력 바이트·저널 대기 상한·부분 기록·종료 후 저장 시간과 실제 저장된 실행 근거의 재생 결과를 포함한다. `/dev/session-viewer.html?theme=light` 또는 `?theme=dark&narrow=1`은 같은 개발 DB로 실제 진단 컴포넌트를 연다. 일반 앱의 목록·스캔 기록은 읽거나 지우지 않는다. 기록 ON/OFF는 별도 실행군으로 비교하고 원본 획득 종료와 배경 저장 완료 시간을 섞지 않는다.

`/dev/canonical-store-proof.html`은 합성 투명 픽셀과 등록한 영상의 ImageBitmap·VideoFrame을 검사한다. 같은 원본의 열린 OPFS 읽기, 입력/복구 두 번 사용과 v4 파일 왕복 후 전체 RGBA 해시가 같아야 한다. 물리 원본 수와 처리 사용 수를 따로 확인한다. 이 작은 왕복 검사는 영상 전체의 인식 정확도나 실시간 처리량 검사를 대신하지 않는다.

`/dev/raster-pipeline-proof.html`은 기본 작업자와 대체 경로를 같은 네이티브 입력으로 세 번씩 비교한다. 두 원본을 소비 전에 제출하고, 투명 프레임 덮어쓰기·전체 RGBA·예약 해제를 검사한다. 이 페이지는 페이지→변환 Worker 경로이며, 실제 기록 Worker 내부의 중첩 실행은 공통 저장소 검사의 `rasterEngine`으로 별도 확인한다. 전체 영상의 기록 처리량은 이후 1배속 검사로 측정한다.

`/dev/scanner.html?native=1`은 이미 구현된 직접 VideoFrame 획득을 명시적으로 켜는 실험 경로다. 일반 앱의 기본 경로를 바꾸지 않는다. 같은 소스에서 query 유무만 달리해 비교하고, 보고서의 `screenOptions.nativeAcquisition`과 실제 설정 사건을 확인한다. 판독 필드·메타데이터·희소 패치의 회귀를 통과하기 전에 기본값으로 승격하지 않는다.

`/dev/monitor-outcome-proof.html`은 공통 저장소와 원본 상태를 같은 합성 시나리오로 비교한다. 수량이 일치해도 미식별 입력이나 미완료 작업이 남으면 확인을 요청하고, 종료·중단된 부분 결과의 위치 기록은 유지한다. `카드 판독 완료`는 표시 상태이며 실제 스캔 검증·자동 종료 조건을 대신하지 않는다. 미식별 입력 건수는 중복 관측을 포함할 수 있어 누락 카드 종류 수와 구분한다. `표시 대상 → 실제 진행창`과 `지연된 전체 상태`로 종료 순간의 오래된 목록 props가 최신 진행 상태를 덮지 않는지 확인한다. 진행 저장소는 종료 후에도 최신 상태를 유지하고, 새 스캔·목록 교체 때 비운다. 밝은/어두운 주변 테마와 좁은 배치는 `?theme=light` 또는 `?theme=dark&narrow=1`로 확인한다.

`/dev/encoded-reference-proof.html`은 개인 실패 기록으로 준비한 복구 영상의 참조 가능성을 검사하는 실험 화면이다. 준비 자료·영상 바이트·독립 원본 픽셀 검증 자료가 모두 있어야 실행한다. 같은 영상 바이트를 순차 디코드하고 전체 RGBA 해시가 맞는 실제 순번·PTS·프레임 길이를 찾는다. 가까운 시각의 프레임으로 대신하지 않는다. `?all=1`은 준비한 전체 후보, `?diff=1`은 원본 RGBA와 바이트 차이·보정 왕복, `?compose=source-over`는 이전 합성 경로를 비교한다. 시각으로 고른 차이 진단은 원본 정체성 증명과 구분한다. 캔버스와 비교 요약만 유지하며 픽셀 프레임을 누적하지 않는다. 디코더 내부 큐와 전체 물리 메모리는 별도 측정 대상이다. 이 검사는 운영 기록 형식을 바꾸지 않으며, 추출 영상의 전체성이나 라이브 네이티브 입력의 동일성을 증명하지 않는다. 바이트 보정이 성공해도 다시 디코드한 기준 SHA가 달라지면 재현은 거부된다. 완전한 참조 저장을 적용하려면 안정된 디코더 픽셀 경로·컨테이너 무결성·트랙·순번·샘플 정보·픽셀 해시와 취소/부분 파일 처리를 함께 검증하는 별도 형식 계약이 필요하다.

기록 Worker는 준비 시 `lz4-wasm`을 한 번 초기화하고 사용할 수 없으면 기존 JavaScript LZ4로 진행한다. 실행 중 인코더 오류는 부분 기록으로 남긴다. `exact.compressionEngine`으로 실제 사용한 경로를 구분하며, 압축 형식과 기존 픽셀 디코더는 같다. 초기화·압축·픽셀 읽기 비용과 전체 스캔 시간은 별도로 비교한다.

dev 보고서의 `sessionEvidence.producedExact`는 임시 기록 producer가 실제 마친 전체 통계다. `metadata.exact`는 브라우저에 남은 파일의 통계이며, 저장 한도 이후 prefix만 남았다면 두 범위가 다르다. producer 성공으로 저장된 파일의 완전성을 대신 증명하지 않는다. 중단 후 복구 통계에서 알 수 없는 값은 계속 `null`이다.

`/dev/scanner.html?rgba=1`은 연속 영상 보완 판독에 `VideoFrame.copyTo({format:'RGBA',colorSpace:'srgb'})`를 쓰는 실험이다. 기본 스캐너는 기존 디코더를 사용한다. 보고서의 `screenOptions.rgbaRecovery`와 frame 사건의 `decoded`를 함께 확인한다. 디코더 sample 순번·PTS와 실제 획득 프레임 ID는 서로 다르며, `rgbaSha256`은 캔버스에 그리기 전 전송 바이트의 해시다. v4 기록은 실제 기록한 픽셀을 별도로 검사한다. 미지원 형식·회전·배율·레이아웃은 오류로 남기며 다른 픽셀 경로로 조용히 대체하지 않는다. 한 프레임씩 전달하더라도 디코더 라이브러리 내부 큐까지 한 프레임이라는 뜻은 아니다. 픽셀 반복성과 실제 판독·종료 시간은 각각 비교해야 한다.

`/dev/native-source-probe.html`은 사용자가 선택한 실제 공유 트랙의 첫 프레임 메타데이터만 확인하고 공유를 자동 종료한다. 픽셀·영상·창/트랙 이름·기기 ID는 보관하지 않는다. 포맷명만 보고 색 행렬을 추측하지 않으며 직접 `MediaStreamTrackProcessor` 경로의 결과를 기본 스캐너의 video wrapper 경로로 일반화하지 않는다. 현재 후보 표시는 좁은 BT.709 프로필만 검사한다. 다른 색 정보가 나와 후보가 아니라고 표시되더라도 공유 실패나 OS 전체 미지원을 뜻하지 않는다. 이탈 시 공유를 중지하며 BFCache 복원 후 다시 검사할 수 있다.

`/dev/native-yuv-proof.html`은 등록한 단일 영상을 두 번 순차 디코드해 네이티브 평면과 고정 CPU 변환의 전체 해시를 비교하는 별도 실험이다. 명시적인 I420/NV12·BT.601(`smpte170m`)/BT.709 제한 범위와 밀집 전체 프레임만 허용하고 미지원 metadata를 해상도로 추론하지 않는다. 같은 평면에서 만드는 signal RGB의 최근접 chroma 확대·반올림 규칙을 recipe로 고정한다. transfer·색역 재매핑을 생략하므로 기존 Canvas·sRGB byte와 같다는 검사가 아니다. 원본 영상 SHA, sample 순번/PTS, native metadata/평면 SHA와 생성 RGBA SHA, 실행 전후 소스를 따로 남긴다. 원본 픽셀 배열은 누적하지 않지만 디코더 내부 큐·GPU·전체 물리 메모리는 별도 측정 대상이다. packed byte 비율을 파일 크기·RAM·스캔 속도 개선율로 바꾸어 보고하지 않는다. 아직 일반 스캐너·기록 형식·기본 입력에는 연결하지 않는다.

`/dev/scanner.html?provider=canvas-control`과 `?provider=native-yuv`는 실제 획득 Worker·판독기를 사용한 필드 비교다. 단일 영상의 **전체 프레임 직렬 검사**, 세션 저장 끔으로 실행한다. 다른 입력·원화 보정 실험과 혼합하지 않는다. 기준은 기존 CanvasSink, 실험은 네이티브 sample의 명시적 색 정보로 고정 변환한 RGBA다. 각각 같은 원본 Blob의 길이·SHA를 먼저 확인하고 새 준비 세션을 사용한다. 모델 준비 비용은 실행 시간에 포함되며 원본 해시 검사는 별도다.

비교 보고서의 모드는 `offline-canvas-control-v1` / `offline-native-yuv-v1`로 분리한다. `providerEvidence`에는 sample 순번/PTS, 생성 전·후의 서로 다른 해시, provider Canvas의 전체 RGBA 해시와 실제 `frame` 사건의 처리 ID를 남긴다. 디코더 순번을 기록된 `provenance.frameId`로 만들지 않는다. Canvas 해시는 획득 Worker 내부의 픽셀 해시가 아니며, 실제 사건 연결도 그 내부 픽셀의 일치 증명을 대신하지 않는다. 새 경로는 opaque RGBA의 생성 해시와 그리기 후 해시가 같아야 계속 진행한다. 원본 복구로 결과를 보완하지 않으며 입력 단계가 섞이면 오류로 남긴다. 원본·평면 SHA·descriptor·생성 RGBA·painted RGBA를 서로 다른 근거로 유지한다.

직렬 비교에는 live admission·대기열·자동 공유 종료·전체 기록 저장 비용이 없다. 시간 지연을 넣어도 실제 공유 처리량 검사가 되지 않는다. 기록 형식과 일반 앱을 바꾸기 전에는 필드 비교 다음에 라이브 입력과 동일 원본 ID 연결, 완전한 기록·재생, 빠른 스크롤·종료 시간 검사를 별도로 통과해야 한다. 버퍼 전송 이후의 RGBA는 호출자가 소유하므로 프레임 배열로 계속 보관하지 않는다. 비교 iterator는 현재 Canvas·읽기 버퍼와 상한 있는 작은 해시 근거만 유지하고, 다음 프레임으로 넘어가기 전에 실제 소비 연결을 확인한다.

성공·실패 픽셀을 짝지어 조사할 때는 위 provider 비교 주소에 `&pairs=97:32,119:20`을 붙이거나 기본 주소 `/dev/scanner.html?pairs=178:15`에서 최대 4개의 관측을 지정한다. provider가 없는 경우는 **일반 단일 영상·offline 전체 프레임 순차 판독·세션 저장 끔·기본 resample**만 지원하며 사진·live·검출 전용·저장 켬·다중 영상과 다른 입력·인식·예열 실험은 준비 전에 거부한다. 앞 숫자는 보고서 `frame` 사건의 **1부터 시작하는 처리 프레임**, 뒤 숫자는 획득 화면의 **0부터 시작하는 칸(0~39)** 이며 원본 디코더 순번과 구분한다. 기존 최대 8개 이미지·바이트 상한 안에서 `pairedCropEvidence`는 같은 관측의 실제 판독 카드와 이름의 초기 128×36 RGBA, crop 좌표·배율, 원본 시각·ID, 시도별 예산·결과를 연결한다. 이름 이미지는 마스크 전 Canvas label이며 최종 신경망 tensor가 아니다. 캐시로 반환한 경우도 초기 label은 전달되므로 label 수를 추론 횟수로 세지 않는다. `diagnosticReadId`는 이 진단만의 순번이며 기록된 실행 attempt ID를 대신하지 않는다.

선택된 작은 입력만 복사하고 PNG·SHA 작업은 스캔 후 별도 단계에서 수행한다. 같은 픽셀의 재시도는 이미지 참조를 공유하고 독립 관측으로 세지 않는다. 한도·취소·저장 실패는 누락 이유와 메타데이터로 남기며, 진단 실패가 인식 결과·완료 판정을 바꾸지 않는다. 이 옵션의 시간은 일반 앱 성능 측정에 섞지 않고 이미지 보존·변환 비용을 따로 확인한다. 개인 이미지가 포함된 보고서는 `fixtures/local/` 또는 `work/`에만 보관한다.

`/dev/name-label-proof.html`은 이 초기 이름 영역만 분리해서 조사한다. 로컬 `work/paired-name-inputs.json`에 버전 1, 소스 해시·run 참조와 최대 8개의 128×36 PNG를 준비한다. 각 항목에는 `key`, `provider`, `processingFrame`, `slot`, `image`, `pngSha256`, `rgbaSha256`, `width`, `height`를 둔다. PNG 바이트 해시와 디코드 RGBA 해시가 모두 원천과 같아야 원본색·회색 RGB의 첫 줄/둘째 줄/전체를 순차 비교한다. 회색식은 `round(.299R+.587G+.114B)`이며 알파를 유지한다. 사전 후보·줄 결합·이름 캐시는 사용하지 않고 각 변형에 독립적인 3초 예산을 준다. 실제 카드의 공유 예산·수락 규칙과 다르므로 이 결과만으로 새 전처리를 기본 적용하지 않는다. 원본색에서 맞던 이름이 회색에서 틀리는 반대 사례도 보존한다.

`?manifest=<failure-name-label-이름-SHA256.json>&recipes=contrast-first-line`은 내용 해시가 붙은 로컬 manifest에서 원본 첫 줄·회색 첫 줄·고정 대비 변환 3종을 비교한다. 새 변환은 1%/99% 히스토그램 stretch와 반경 3·gain 8의 local dark/absolute mean 차이이며, 분위수 정의·실제 한계·경계·clamp·반올림·알파 정책을 결과 recipe에 남긴다. 대비 실험은 불투명 128×36 입력만 받고 첫 18행을 새 배열로 만든다. 입력·PNG·디코드 RGBA·변환 RGBA·Canvas readback 해시를 구분하며 모델 내부 텐서의 바이트 증거로 해석하지 않는다. 같은 PNG의 다른 변환은 독립 관측이 아니다.

서로 다른 producer 소스는 한 소스 해시로 합치지 않고 별도 manifest로 실행한다. `normal-acquisition` 입력은 실제 `runSha256`과 전체 `source`를 보존하고 같은 provider의 정확한 run 참조에 연결해야 한다. 물리 원본 ID가 미기록이면 `null`을 유지한다. 이전 canvas/native 입력에 없던 출처를 추정해 추가하지 않는다. 선택 경로는 basename·고정 recipe family만 허용하고 외부 URL·임의 임계값·카드 후보를 받지 않는다. 결과는 변환 시간·해시/paint 시간·OCR 대기·전체 변형 시간을 나눠 저장한다. OCR의 기존 `elapsedMs`는 대기 시간 의미를 유지한다. 실행에는 6분 상한이 있고 마지막 소스 확인은 별도 최대 10초이며, 최종 확인 중 취소돼도 완료로 보고하지 않는다. 이 페이지의 비교 결과는 일반 스캐너나 카드 목록에 적용되지 않는다.

`recipes=color-first-line`은 같은 입력에서 원본·회색 첫 줄과 chroma/R/G/B 변환 4종을 비교한다. chroma는 `max(R,G,B)-min(R,G,B)`이며 각 scalar의 고정 1%/99% stretch 뒤 chroma만 반전한다. 채널과 수식은 사전에 고정하고 이름·후보·등급에 따라 선택하지 않는다. 원본색의 차이를 회색 변환 전에 조사하는 개발 실험이며, 높은 모델 신뢰도만으로 전처리를 채택하거나 카드 이름을 확정하지 않는다.

`/dev/card-crop-proof.html`은 고정 개인 입력 `work/card-crop-inputs.json`의 140×210 카드 PNG 최대 8개를 실제 전체 판독기로 비교한다. 버전 1 입력 계약은 [`card-crop-proof-core.ts`](../dev/card-crop-proof-core.ts)의 `CardCropProofData`·`CardCropInput`·`CardCropSource`와 `CARD_CROP_PROOF_LIMITS`를 따른다. 실행 파일 SHA·소스 digest를 가진 run 참조, 세션·관측·원본/획득/처리 프레임·캡처 순서/시각·phase·slot, PNG 바이트와 디코드 RGBA SHA-256을 정확한 원천에 묶어 준비한다. run 참조는 선언 메타데이터이며 이 페이지가 원본 run 파일을 다시 읽어 증명하지 않는다. PNG당 128KiB·입력 전체 2MiB 상한이며 입력과 결과는 `work/`에만 보관한다.

입력 순서대로 `baseline`과 `gray-first-line-opt-in`을 실행하며 입력·모드마다 새 판독기를 준비한다. 준비 시간과 카드 판독 시간을 분리하고, 이름 식별·각성/장수·조건부 장수 재확인은 카드당 같은 3초 예산을 공유한다. 알 수 없는 안정성·테두리 정보는 보수적인 false/0으로 전달하며 원래 획득 수락을 재구성하지 않는다. 같은 크롭을 새 독립 관측으로 세지 않는다. `candidate`는 진단 주석으로만 보존하고 판독기 인자·후보 필터·정답으로 쓰지 않는다. 결과는 입력 파일·실제 PNG/RGBA 해시, 입력 제작 소스와 비교 실행 전후 소스를 별도로 남기고 이름 시도·필드·확인 사유를 보존한다. 이름 없는 필드는 카드에 연결되지 않은 진단이다. 잘린 카드 재판독 비교이므로 원래 획득·스케줄·목록 병합, 인간 정답, 실시간 처리량·공유·UI 지연의 증명이 아니다.

고정 실패 크롭은 `?manifest=failure-card-crop-사례명-SHA256.json&comparison=portrait-registration`으로 선택한다. 실제 파일명에는 영문 소문자·숫자·하이픈의 사례명과 파일 바이트의 소문자 64자리 SHA-256을 사용한다. `work/`의 파일명만 허용하며 경로·외부 URL·중복 옵션을 거부한다. 파일명 해시와 기존 v1 입력 계약을 모두 확인한 뒤, 회색 이름 보완을 끈 `baseline`과 `fractional-registration-opt-in`을 비교한다. 이름 원본 정책은 두 모드 모두 명시적인 `resample`이며 실제 판독기 설정도 결과에 기록한다. 제작자가 선언한 RGBA 해시와 브라우저가 디코드한 픽셀의 검증은 따로 표시한다. 이 선택은 기본 입력 포인터나 앱의 인식 기준·기본 설정을 바꾸지 않는다.

준비·판독 오류나 판독기 정리 미확정이 발생하면 해당 행을 보존하고 다음 모드를 시작하지 않는다. 종료 소스 확인 도중 취소된 실행도 부분 결과로 남긴다. RGBA 불일치에는 실제 계산된 해시를 보존하되 인식은 시작하지 않는다.

`?gray=1`은 실패한 이름의 정밀 재시도에만 회색 첫 줄을 추가하는 개발 실험이다. 일반 영상·사진 입력과 영상 1배속 경로에서 사용할 수 있으며, `?provider=canvas-control&gray=1`과 `?provider=native-yuv&gray=1`의 입력 비교도 유지한다. 원본색 판독·독립 원화 확인이 먼저이며, 기존 카드 예산 안에서 사전 후보·줄 결합 없는 추론을 한 번 추가한다. 정확한 이름과 기존 확정 조건을 만족한 결과만 사용하고, 미확정 회색 후보나 캐시로 기본 경로를 바꾸지 않는다. `validation.nameOptions`·설정 사건의 `grayFirstLineFallback`·실제 이름 진단의 전처리 표시를 함께 확인한다. 일반 앱의 기본 동작은 바꾸지 않으며 다른 정렬/위치/원화 보정 실험과 혼합하지 않는다. 동일 소스의 켠/끈 실행에서 정상·실패 관측과 최종 필드·미식별 수를 함께 비교한다.

`acquisition-capture`는 품질 선별 전에 모든 획득 칸의 원래 격자·최종 크롭·미리보기 좌표, 원본/획득/처리 ID, 정지 판정 출처와 최종 품질 판정을 남긴다. `complete`는 획득기가 실제 사용한 원래 격자 경계 검사값이며, 나중에 최종 크롭만 보고 다시 계산하지 않는다. 이전 저장 분석에 없는 값은 `null`이다. 원본 ID가 있다는 사실은 저장 ACK를 뜻하지 않는다.

`recognition-capture`는 실제 이름 선택 경계에서 사용한 정지·정렬·단계·전처리 옵션과 획득 관측 tuple을 기록한다. `invocationId`는 진단용 이름 선택 순번이며 실행 attempt나 신경망 추론 횟수가 아니다. 이미 확정한 이름 재사용과 visual Worker 결과도 별도 경로로 표시한다. [`capture-provenance.ts`](../src/features/card-scanner/capture-provenance.ts)의 엄격한 메타데이터 계약만 사용하고 픽셀·후보 정답은 넣지 않는다. 두 사건은 상태·완료 판정에 사용하지 않는다. 기록 실패는 부분 기록으로 남기며 이 진단만으로 원래 스케줄이나 전체 판독을 재현했다고 해석하지 않는다.

이미 확정된 같은 원본의 복구는 크롭을 만들지 않을 수 있다. 새 획득 기록은 `cropState: 'omitted-resolved'`와 두 크기 `null`로 이를 표시하며, 품질·좌표는 저장된 분석에서 왔음을 유지한다. `materialized`만 실제 크롭 크기를 가진다. 과거에 `cropState`가 없는 진단의 크기만으로 실제 크롭이 생성됐다고 판단하지 않는다.

영상의 `media-lineage`는 decoder iterator별 시작·표본·종료와 `original-file`/`re-recorded-video` 역할을 남긴다. 순번은 이 iterator가 내보낸 값의 순서이며 원본 컨테이너 프레임 번호가 아니다. 같은 Blob 객체는 약한 참조로 같은 지역 ID를 가지지만 이는 내용 SHA가 아니다. URL 요청 ID도 실제 파일 바이트를 증명하지 않는다. EOF·중도 return·취소·오류를 구분하며 EOF는 이 iterator의 종료만 뜻한다. `media-input-link`는 같은 프레임 envelope에 실려 온 표본을 실제 처리/획득 ID에 연결하고, 다른 시계나 가까운 PTS로 연결을 만들지 않는다. 이전 원본 스냅샷은 직전 디코더의 계보를 상속하지 않는다.

개발 1배속 실행의 `source-playback`은 captureStream 앞의 원본 video 요소에서 raw 표시 callback을 기록한다. 중복 미디어 시각도 보존하고, callback 순번·브라우저의 `presentedFrames`와 자연 종료 여부를 decoder 순번과 구분한다. `sourcePlaybackOrigin`의 입력 이름·SHA는 요청에 사용한 입력 설명이며 재검증한 바이트의 증거가 아니다. 이 진단은 입력을 복사하거나 제어하지 않으며 실패는 부분 기록으로 남긴다. 원본 표시 → target 도착 → 재녹화 사이의 같은 프레임 연결은 별도 증거 없이는 미확인이다.

## 회귀 검사와 결과 해석

`/dev/scanner.html?names=continue`는 빠른 이름 판독에서 거절된 원본색 결과를 같은 이름 판독 호출의 정밀 단계에 이어 쓰는 개발 실험이다. 기본값과 `?names=resample`은 기존 재요청 방식을 유지한다. 기본 영상·이미지의 순차 검사와 영상 1배속에서 실행할 수 있으며, 다른 입력·전처리 실험과 혼합하지 않는다. 순차 검사는 원본 표본·필드 비교용이며 실시간 처리량 검사와 구분한다. 카드 간 캐시나 독립 관측을 추가하지 않고 같은 예산·취소 신호를 유지한다.

이름 판독 설정은 버전이 있는 `nameConfiguration`으로 전달한다. 일반 앱은 `resample`을 명시하며 예열한 모든 판독기와 실제 스캔의 설정을 대조한다. 준비 모듈이 발급한 엔진만 한 번 인계할 수 있고, 다른 설정·변조된 엔진·이미 사용 중인 엔진은 거부한다. 앱이 소유한 대기 엔진이 기록의 설정과 다르면 종료가 끝난 뒤 해당 설정으로 새로 준비한다. 취소·설정 오류로 거부된 다른 실행이 이미 인계된 엔진을 종료하지 않도록 소유권을 구분한다.

watchdog가 사용자에게 중단을 반환하는 시점과 실제 판독 작업·소유 자원 종료가 끝나는 시점은 다르다. 엔진 종료 통지는 실제 작업과 종료 Promise가 합류한 뒤 한 번만 발행한다. 일반 앱은 이 통지를 기다리는 동안 새 예열·공유 스캔·재현 실행을 시작하지 않는다. 진단 창을 닫아도 이 제한은 유지하며 카드 목록 확인은 계속할 수 있다. 통지 자체가 OS·GPU 자원의 완전 회수를 증명하지는 않는다.

`?warm=1`은 기본 영상·이미지 입력에서 실제 예열 엔진의 인계를 검사한다. `?names=continue&warm=1`은 같은 설정으로 예열한 엔진을 쓰며, 일반 앱 기본값을 변경하지 않는다. 다른 입력 실험·회색조·일괄 비교와 함께 실행하지 않는다. 보고서의 `nameOptions.prepared`는 이 검사의 요청 설정이며, 실제 설정 사건과 각 판독기의 통계를 함께 대조해야 한다. 예열 비용도 개별 실행 경과 시간에 포함된다.

새 `.loareplay`와 복구용 초기 정보는 실제 이름 판독 설정을 보존한다. 재현은 보관된 설정으로 실행하며, 설정이 없는 이전 기록은 미기록으로 표시하고 현재 기본값으로 비교한다. 이전 기록에 당시 설정을 추정해 덧붙이지 않는다. 자동 진단의 설정과 `performance.nameOcr`도 실제 상태에서만 가져오며, 서로 다른 정책의 판독기 통계가 있으면 지우지 않고 남긴다.

`performance.nameOcr`는 종료 후 판독기별 한국어 신경망 이름 요청·재사용·실패 수와 고정 전처리별 대기 시간을 남긴다. Tesseract 보완 요청은 이 집계에 포함되지 않으며 모델 내부 캐시 적중을 실제 추론 실행으로 세지 않는다. `wallAwaitMs`에는 요청 안의 준비·큐·Worker 응답 대기가 포함되므로 신경망 계산 시간이나 전체 스캔 시간으로 해석하지 않는다. 통계는 판독기 32개·고정 전처리 14개·64KiB 이내로 복사하고, 잘못되거나 큰 통계는 누락 사유를 남긴다. 진단 용량이 부족하면 새 통계를 먼저 제외해 기존 필드·이미지 근거를 보존한다. 실제 모델의 결과·예산 경계·영상 검증 전에는 일반 앱의 기본 동작을 바꾸지 않는다.

일반 사진은 `imageInputs`의 이미지 요소 목록 또는 URL 목록으로 전달하며 재현 입력으로 표시하지 않는다. URL 목록은 한 장씩 디코드하고 소비·취소·실패 뒤 해제한다. 순서·중복·합성 시각 0을 유지하며, 이 시각을 실제 촬영 시각이나 저장된 원본 근거로 사용하지 않는다.

개발 검사의 일반 영상 준비는 `loadVideoInput`이 담당한다. `loadeddata` 사건만으로 성공하지 않고 현재 요청의 URL·재생 가능한 데이터 상태를 함께 확인한다. 기본 대기 한도는 15초이며 취소·시간 초과 시 해당 요청의 읽기를 중지하고 부분 실행으로 남긴다. 같은 영상 요소의 중복 준비는 거부하며 이전 요청의 지연된 사건으로 새 요청을 완료하지 않는다. 자동 재시도로 입력 순서나 표본을 바꾸지 않는다. 영상 준비 대기는 `runScanner`가 시작되기 전이므로 스캐너 watchdog과 별도로 제한한다. `preload=auto`는 브라우저에 주는 준비 힌트이며 모든 로딩 지연의 원인을 해결했다는 뜻은 아니다.

보고서의 `performance.inputPreparation`은 일반 순차 영상의 준비 시작·종료 시각, 제한, 결과와 대기 시간을 남긴다. 시계는 페이지의 `performance.now()`이며 원본 PTS나 스캐너의 입력 프레임 시각이 아니다. 사진·다른 입력 경로는 `null`로 남긴다. 이 대기를 OCR 처리 시간에 합쳐 해석하지 않는다.

`/dev/scanner.html?fps=4`(또는 `fps=6`, `fps=8`)은 전체 입력 복사의 최소 간격을 제한하는 개발 실험이다. 진행창 위치 샘플과 판독기 수는 바꾸지 않지만 실제 수집 프레임 선택은 달라진다. 기본 앱에는 제한을 추가하지 않는다. `screenOptions.minInputIntervalMs`와 각 입력 선택 사건의 gates를 확인하고, 같은 프레임 집합의 처리량 개선으로 오해하지 않는다. 제한한 간격과 캡처 시각은 별개이며 판독 완료 시각을 카드 최신값으로 바꾸지 않는다. 빠른 스크롤의 누락·최신 필드·기록 전체성과 실제 화면 반응을 따로 통과해야 한다.

`/dev/scanner.html?fractional=1`은 이름이 확정되지 않은 정밀 재시도에만 세밀한 원화 위치 보정을 적용한다. 기본 앱에서는 꺼져 있다. `screenOptions.fractionalPortrait`·설정 사건의 `portraitRegistration`과 실제 카드 근거의 `portrait.registration`을 구분해서 본다. 플래그가 켜졌다는 사실만으로 그 판독에서 보정이 실행되거나 성공했다고 해석하지 않는다. 전체 경로에 추가 탐색을 적용하는 방식은 수집 처리량을 해칠 수 있어 기본 경로로 사용하지 않는다.

`/dev/compact-store-proof.html`은 실제 저장 Worker와 독립 개발용 브라우저 저널에 작은 native/RGBA 혼합 파일을 저장한다. 합성 I420/NV12·RGBA와 선택한 코퍼스 영상의 1·3·5초 표본을 사용하며, 열린/닫힌 저장소 랜덤 읽기·v5 내보내기/다시 열기·전체 물리 픽셀 SHA·반복 원본 사용·종류별 총량을 검사한다. 영상 원본 Blob SHA와 실행 전후 소스를 확인한다. 내보낸 파일은 코퍼스에 별도로 등록하고 파일 전체를 스트림으로 해시한다. 생성한 사용 사건은 실제 스캐너 획득이나 인식 정확도의 근거가 아니며 전체 영상·OS 공유·512MiB 전체 기록 gate는 통과하지 않은 상태로 남긴다.

주요 경계 조건은 다음 테스트에 유지한다. 로직을 바꾸면 해당 검사를 먼저 실행하고 전체 `npm test`, lint, build를 확인한다.

예를 들어 위치 변경은 `node --import tsx --test tests/inventory-position.test.ts tests/scan-grid.test.ts`로 확인한다. 성능 비교는 같은 영상·해상도·빈 시작 목록을 사용하고 기록 옵션을 함께 적는다. 전체 입력 기록을 끈 실행과 켠 실행은 비용이 달라 직접 섞어 비교하지 않는다. 공유 종료 시각, 최종 판독 종료, 목록 저장, 진단 저장 완료를 구분한다. 마지막 식별 입력 이후 10초 이내 종료 목표는 실제 공유 또는 실시간 재생으로 확인하고, 입력을 강제 종료해서 자동 종료 성능으로 보고하지 않는다.

개인 입력이 없는 새 환경의 검증은 추적 파일만 있는 별도 디렉터리에서 `npm ci`, lint, test, Pages base build와 `npm run audit:distribution`을 수행한다. 빌드 자산의 경로·MIME·manifest 해시와 개발 화면/개인 자료의 배포 제외 여부도 확인한다. 해시를 검사하는 외부 고지·OCR 문자표는 `.gitattributes`의 줄바꿈 변환 제외를 유지한다. 모델 최초 다운로드와 기존 캐시 사용을 구분하고, 외부 고지 누락·청크 경고는 현재 검사 출력에 따라 보고한다. 특정 시점의 테스트 개수나 단일 사진 성공을 현재 전체 카드 정확도로 일반화하지 않는다.

## 스캔 진단과 입력 재현

공통 입력의 바이트 연결은 `/dev/prepared-source-proof.html`에서 검사한다. 실제 준비·획득·저장 Worker와 브라우저 저널을 거쳐 내보낸 v5 파일을 다시 열고, 내부 raster 해시·저장 ACK·복원 입력을 비교한다. 합성 I420, 같은 입력의 raw fallback, 선택 영상의 표본, 미사용 백업과 이전 원본의 재사용을 포함한다. 표본 검사이며 전체 영상 판독이나 실제 공유 성능 검사는 아니다.

파일 봉인 뒤 복원 검사가 실패해도 **미검증 파일 저장**으로 같은 바이트를 보존할 수 있다. 실패 결과의 `complete:false`·세션 ID와 함께 코퍼스에 등록하며, 파일이 저장됐다는 사실을 복원 성공으로 해석하지 않는다. 전체 검증을 통과해야 버튼과 파일 이름이 검증 완료 상태로 바뀐다.

`/dev/prepared-attestation-proof.html`은 고정 시작 시각 이후 준비 운동 1개와 연속 30개 영상 표본으로 준비→별도 검증 Worker의 전용 포트를 검사한다. native 재변환 경로와 전용 포트의 계산 근거를 사용한 해시 검증 경로를 순서대로 실행하고, 실제 획득 전체 raster·독립 RGBA 복원·칸 geometry/품질이 같아야 한다. 원본 checksum과 실행 전후 소스를 확인하며 전체 영수증은 결과 JSON에 저장한다. 이 화면은 파일 쓰기·저장 ACK·OCR·실제 공유를 실행하지 않는다. 작업자 검증 시간은 전체 스캔 속도나 실제 기록 성능과 구분하며, 기존 기록 계약과 기본 스캐너를 자동으로 교체하지 않는다.

실시간 통합 실험은 `/dev/scanner.html?prepared=1`에서 **영상 1배속**, **자동 세션 저장**, 실제 판독 모드로 실행한다. 아래에 명시된 조합 외에는 다른 입력·인식 실험 옵션과 섞지 않는다. 기본 경로는 바뀌지 않는다. 원본 큐·저장 ACK·부분 기록 여부, 전체 물리 픽셀, 실제 측정/분석 재사용 영수증과 상태 영역을 함께 검사한 뒤 채택 여부를 결정한다. 이 실험은 기록 OFF의 성능을 대표하지 않는다.

준비 Canvas와 v6 기록을 함께 검사할 때는 `/dev/scanner.html?prepared=1&preparation=canvas&codecPolicy=rgba-window-32m-eight-v1`을 사용한다. 같은 준비 RGBA의 획득·저장 연결을 검사하는 조합이며 native/auto 준비 또는 `attest=1`과 이 codec을 함께 사용하지 않는다. 파일 복원 해시와 상태 재생 일치는 OCR 재판독 정확도 또는 OS 화면 공유 지연의 증명이 아니다.

저장 한도 실패를 재현하려면 위 주소에 `&recordingBudgetMiB=490`처럼 **32~512의 정수**를 지정한다. 생략하면 개발용 512MiB이며, 명시한 값마다 별도 개발 DB를 사용한다. 제품 한도를 늘리거나 기존 사용자 기록을 삭제하지 않는다. DB에 남은 기록과 다른 세션의 예약도 공간을 사용하므로 값만 같다고 매번 동일한 실패가 발생하지는 않는다.

한도로 중단된 기록의 보완 여부는 `sessionEvidence.exactFinalization`에서 확인한다. 살아 있는 동일 producer의 완전한 바이트·실제 획득 근거·상태 체크포인트와 저장 prefix가 검증되고 최종 파일이 한도 안에 들어갈 때만 미리보기를 제외하고 나머지 원본을 원자적으로 저장한다. 원본 자체가 한도보다 크거나 근거가 부족하면 부분 기록을 유지한다. 영수증이 없으면 보완 경로를 검증한 실행으로 세지 않는다. 판독 완료까지의 시간, 기록 종료 시간, prefix 해시 시간은 각각 비교한다.

개발 결과의 `sessionEvidence.finalizationMs`는 세션 종료와 색인 조회, 저장된 실행 기록의 재검증을 합친 시간이다. `timings.finishMs`, `indexReadMs`, `executionSummaryMs`로 구분하며 실행하지 못한 단계는 `null`로 남긴다. `finishMs`도 producer/journal 합류·청크 조회·봉인·부분 prefix 검사·자원 정리를 포함할 수 있어 디스크 쓰기 시간으로 단정하지 않는다. 실제 앱은 판독 완료 후 목록 사용을 먼저 재개하고 진단 저장을 별도로 마무리한다. 이 백그라운드 작업의 CPU/I/O 경합과 저장 완료 시각은 따로 측정한다.

`sessionEvidence.finishTiming`은 세션 내부의 등록·producer 종료·journal 합류와 drain·봉인 전후 load·봉인·파일/prefix 검사·정리를 구분한 진단 스냅샷이다. 완료 전 총 시간과 미실행 단계는 `null`이며 실패 단계도 별도로 남긴다. 파일/prefix 검사와 cleanup은 기존처럼 겹칠 수 있어 단계 시간을 더해 총 시간으로 쓰지 않는다. 저장 ACK·완료 판정·입력 시각에는 사용하지 않는다.

`prepared=1&preparation=canvas`는 지원되는 VideoFrame도 기존 준비 Worker의 Canvas 경로로 직접 그린다. 기본 `auto`의 native 선택과 구분하며 `rgba`·`canvas-requested` 결과와 실제 완료 모드를 기록한다. `attest=1`과 함께 사용하지 않는다. `/dev/prepared-source-proof.html?preparation=canvas`에서 같은 owned 입력을 기본 획득 Worker와 준비 Canvas에 순서대로 보내 전체 RGBA 해시·최종 카드 Canvas·geometry·quality를 먼저 비교한다. 획득 Worker의 `putImageData → 실제 readback/hash` 영수증, 저장 ACK와 복원 검사는 유지한다. 이 표본 검증은 변환·readback을 준비 Worker로 옮기는 것이며 readback 1회 제거·일반 화면 공유의 속도 향상 증명이 아니다.

`/dev/scanner.html?prepared=1&attest=1`은 이 실험의 native 저장에서 준비 Worker가 이미 계산한 변환 근거를 사용한다. 실제 기록 Worker가 생성한 전용 포트를 준비 Worker에 한 번 전달하며 native 전체 바이트·descriptor·recipe 해시를 다시 검사한다. 일치한 `stored-attested` ACK는 일회용 ticket과 원본 ID·캡처 시각·크기·RGBA 해시를 연결한다. 티켓을 일반 프레임 JSON에 넣는 것으로 이 기능을 켤 수 없다. RGBA 대체는 기존 독립 경로를 사용하며 기본 앱에는 적용하지 않는다.

실제 저장·획득·복원 표본 검사는 `/dev/prepared-pipeline-proof.html?attest=1`에서 실행한다. 양쪽 모드 모두 저장을 켜고 고정 구간의 원본 31개(준비 운동 1개 포함)를 사용한다. OPFS 열린 파일 랜덤 읽기와 전체 순차 복원, 실제 획득 raster, 별도 저장 근거 메타데이터를 함께 확인한다. stage 합산은 겹칠 수 있으며 이 표본 결과를 전체 스캔·OS 공유 지연이나 전체 기록 성공으로 보고하지 않는다. 저장 전 변환을 생략하더라도 재현의 native→RGBA 독립 변환·전체 SHA 검사는 유지한다.

`/dev/prepared-pipeline-proof.html?attest=1&raster=compare`는 카드 획득·전송을 비교한다. `raster-control`은 기존 Bitmap 전송과 재사용 끔, `raster-reuse`는 측정 배열 재사용과 owned 픽셀 전송이다. 두 모드 모두 동일한 한 프레임 선행 준비를 사용한다. 모든 카드의 최종 main Canvas(실제 OCR 소비 입력) RGBA SHA도 비교한다. 이 SHA는 전송 전 raw 바이트나 OCR 성공률의 증명이 아니다. 카드 readback·해시를 추가한 검증 비용은 측정 루프에 포함되며 두 변경을 묶은 단일 순서 비교다. 세부 시간만 보고 전체 스캔 배수나 순수 재사용 효과를 단정하지 않는다.

진단 이미지 UI를 검사할 때는 실제 검증 보고서의 `diagnosticSummary`만 개인 `work/session-viewer-summary.json`에 복사하고 `/dev/session-viewer.html?summary=1`을 연다. `theme=dark&narrow=1`로 어두운 테마와 좁은 대화상자를 확인한다. 이 경로는 최대 3MiB의 고정 로컬 요약만 읽고 브라우저 기록을 변경하지 않는다. 입력 픽셀이 없는 요약이므로 재현이나 저장소 동작 검사로 해석하지 않는다.

**사용법 → 문제 해결 → 스캔 진단**은 세션별 입력과 작은 진단 요약을 제공한다. 입력은 기본으로 기록하며 **입력 기록 보관**에서 끌 수 있다. **입력 재현 시작**은 보관된 픽셀 해시를 검증하고 반복 판독한다. **기록 파일 저장**으로 `.loareplay`를 보관하고 다른 브라우저나 개발 버전에서 **기록 불러오기**로 같은 파일을 선택한다. 요약 JSON에는 입력 프레임이 없으므로 재현에는 사용할 수 없다. 입력 재현 화면의 추가/누락/변경을 비교하되 원래 결과는 정답 라벨이 아님을 구분한다. 중지·누락 기록은 부분 결과로 표시하며 실제 카드 목록·백업은 바뀌지 않는다. 기록 ON/OFF의 수집·판독·종료 비용 검증은 배포 전 별도 통과 조건이다.

전체 입력 기록 파일에는 공유 화면 전체와 시작 목록이 포함된다. 먼저 영상 미리보기를 확인하고 공개 이슈 첨부 여부를 사용자가 결정한다. 이슈에는 문제 카드·발생 조건·코드/데이터 버전을 함께 적는다. 개인 기록 파일은 `work/` 또는 `fixtures/local/`에만 두고 커밋하지 않는다. 기록 구조와 메모리 한도는 [스캐너 구조](scanner-pipeline.md#최근-스캔-재현)를 따른다.

진단 창에서 파일을 읽거나 검사하는 동안에도 중지·Esc·닫기가 동작해야 한다. 브라우저 저장소 응답 지연과 늦게 끝난 작업을 포함해 창 재열기 시 이전 결과가 덮어쓰지 않는지 확인한다. 스캔 종료 직후 진단 저장 중 창을 열었을 때 작업 버튼이 잠기고, 저장 완료 후 최신 요약·파일이 자동 표시되는지도 확인한다. 카드 목록은 진단 저장 성공 여부와 독립적으로 복원되어야 한다.

### 이름 확인 이후 판독 대기 분석

개발 실행 보고서의 순서 검증된 실행 기록을 분석한다. 개인 보고서는 `work/` 또는 `fixtures/local/` 안에 둔다.

```sh
node --import tsx scripts/analyze-recognition-tail.mjs work/run-report.json
```

보고서 SHA-256, 이름 확인 시각 이후의 판독 사건 수, 같은 관측 재시도, 후보 그룹 분리, 필드 revision 변경을 출력한다. 서로 다른 그룹이 최종적으로 같은 카드 ID에 연결됐는지도 집계한다. 최종 ID는 사후 분석에만 사용하며 초기 판독을 건너뛰는 근거가 아니다. 이 도구는 입력·목록·기록을 수정하지 않는다.

`status: unmeasured`는 판독 사건이 없는 기록, `partial`은 누락·부분 기록 또는 연결되지 않은 획득/그룹 근거를 뜻한다. 미측정을 0건 작업으로 해석하지 않는다. 이름 확인 시각이 없으면 분석을 거부한다. 사건 수는 모델 추론 횟수·CPU 시간·정답률이 아니며, 픽셀·필드 revision 또는 그룹이 같다는 이유만으로 최신 관측을 삭제하지 않는다.

`/dev/visual-pixel-proof.html`은 시각 판독 Worker의 ImageBitmap → OffscreenCanvas 입력과 기존 정규화 Canvas를 비교한다. 140×210 불투명 표본은 실제 픽셀 SHA-256, 이름/보석 검사, 장수 판독 결과가 같아야 한다. 투명·다른 크기 입력은 재사용하지 않는지만 검사하며 결과 동일성을 주장하지 않는다. 보석 fixture와 합성 표본 검사이므로 전체 영상 회귀·처리량 측정을 대체하지 않는다.
