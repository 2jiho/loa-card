# 개발용 화면 공유 기록·재실행

개발·테스트 전용이다. 개발자가 화면 공유로 스캐너를 쓰면 **스캐너가 카드 창(격자)을 잡은 구간(앞뒤 2초 포함)의 프레임을 전부 서버에 바로 저장**하고, 저장된 기록을 언제든 같은 입력으로 다시 실행해 코드 버전별 결과를 비교한다. 카드 창이 없는 시간(다른 창, 대기)은 저장하지 않으므로 용량과 재실행 시간이 크게 줄어든다. 배포 앱에는 포함하지 않는다(`vite serve` 전용 플러그인, `import.meta.env.DEV` 분기). 기존 브라우저 저장소(IndexedDB) 기반 기록과 독립적이며 호환하지 않는다. 보안은 범위 밖이다(로컬 개발 전용).

## 목표와 비목표

- 새로고침·브라우저 저장소 초기화·탭 종료와 무관하게 공유 중 받은 프레임이 서버 디스크에 남는다.
- 브라우저 메모리·저장소 한도에 묶이지 않는다. 용량은 서버 디스크가 정한다.
- 기록은 판독을 기다리게 하거나 늦추지 않는다. 기록기가 뒤처지면 프레임을 버리고 그 개수를 기록에 남긴다.
- 재실행은 서버가 프레임을 디코딩해 흘려 주므로 브라우저 메모리를 쓰지 않는다.
- 비목표: 보안, 배포 앱의 기록, 기존 `.loareplay` 호환.

## 저장 형식

`fixtures/local/recordings/<id>/` (Git 제외 영역)

| 파일 | 내용 |
|---|---|
| `meta.json` | id, 시작 시각, 크기, `pixelFormat`, `colorSpace`, `codec`, 상태(`open`/`sealed`), 프레임 수, 완전성, 파일 해시, 메모, 환경 |
| `frames.mkv` | 저장한 모든 프레임. 무손실(YUV는 x264 qp 0, RGBA는 Ut Video). 프레임 번호 = 순번 |
| `frames.jsonl` | 프레임마다 한 줄: `seq`, `mediaTimeMs`, `deliveredAtMs`(세션 시작 기준), `receivedAtMs` |
| `runs/run-*.json` | 이 기록의 재실행 보고서(요약 + 카드 목록) |

- `frames.jsonl`이 시각의 기준이다. mkv의 pts는 쓰지 않는다.
- 픽셀 형식: 공유 영상의 **원본 YUV**(`i420`/`nv12`)를 변환 없이 저장한다(프레임당 1.5바이트/픽셀). 원본 레이아웃을 알 수 없는 프레임은 `rgba`로 대체한다. NV12는 정확한 재배열로 I420로 보관한다.
- 코덱(2026-11-11 이후): 원본 YUV(`i420`/`nv12`)는 **x264 무손실(`-preset ultrafast -qp 0`, `meta.codec: h264-lossless`)**로 저장한다. 스크롤하는 목록은 이웃 프레임이 거의 같아서, 실제 공유 304프레임(2560×1440)이 Ut Video 599MB에서 74MB로 줄었다(약 8배). 인코딩 약 300fps, 디코딩 속도는 Ut Video와 같고, 디코드한 1.68GB가 바이트 단위로 같음을 확인했다. `ultrafast`는 B프레임·선행 탐색이 없어 비정상 종료한 기록도 마지막 프레임까지 디코딩된다. RGBA 대체 형식은 계속 Ut Video다. 아래는 그 이전 선택 근거다.
- 코덱(이전): Ut Video. 같은 무손실이면서 단일 슬라이스 FFV1보다 인코딩 약 5배(220 대 40fps), 디코딩 약 16배(405 대 25fps) 빠르고 약 13% 더 크다(2560×1440 실제 공유 150프레임 측정). 재실행은 디코딩이 기록 속도보다 충분히 빨라야 스캐너와 CPU를 나눠 써도 간격을 지킨다. 이전 FFV1 기록은 그대로 읽힌다.

## 흐름

1. 개발 서버에서 화면 공유 스캔(`runScanner`, `source==='screen'`)이 시작되면 기록기가 공유 영상 트랙을 복제해 `MediaStreamTrackProcessor`를 만들고, 그 프레임 스트림(`readable`)을 워커로 넘긴다. 프레임은 워커가 직접 읽으므로 스캐너가 메인 스레드를 바쁘게 써도 기록이 굶지 않는다(메인 스레드에서 읽었을 때는 스캐너가 바쁜 동안 프레임이 초당 약 29개에서 2~3개로 줄었다).
2. 워커는 프레임마다 `VideoFrame.copyTo`로 원본 바이트를 복사해 메모리 링(최대 약 2초·320MB)에 둔다. 스캐너가 카드 창을 찾을 때마다(`offerLocated`) 기록기에 신호를 주면, 워커는 링의 최근 2초와 이후 2초의 프레임을 `PUT /__rec/<id>/start`, 이어서 프레임마다 `POST /__rec/<id>/frame`(원시 바이트 + 시각·순번 헤더, 최대 8개 동시)으로 올린다. 서버는 순번대로 쓴다(`x-seq`). 카드 창과 먼 프레임은 링에서 밀려나 저장되지 않는다.
3. 서버가 ffmpeg(`ffmpeg-static`)에 프레임을 흘려 쓰고 `frames.jsonl`에 줄을 더한다.
4. 종료 시 `POST /__rec/<id>/seal`. 카드 창이 있는 구간만 프레임이 오므로 조용한 시간이 길 수 있어, 10분 동안 프레임이 없을 때만 서버가 자동 봉인한다(페이지 종료·크래시). 봉인되지 않은 채 남은 기록(서버 재시작 등)은 `POST /seal`로 복구한다: 실제 디코딩되는 프레임만 인정하고 `complete:false`로 표시한다.
5. 재실행(`/dev/recording.html`): `GET /__rec/<id>/frames`가 ffmpeg 출력을 그대로 흘려 주고, 브라우저가 프레임을 조립해 `VideoFrame`으로 만들어 `MediaStreamTrackGenerator`에 기록된 간격대로 쓴다. 스캐너는 진짜 공유와 같은 `MediaStream` 트랙을 받는다. 색 정보(primaries/matrix/range)도 함께 복원한다.

## 정직한 범위

- 재현하는 것: 카드 창이 보인 구간(앞뒤 2초 포함)에서 기록기가 받은 모든 프레임의 픽셀(원본 YUV, 아니면 RGBA), 순서, 간격. 스캐너가 처리했는지와 무관하므로 스캐너가 빨라져 더 많은 프레임을 처리해도 같은 기록으로 시험할 수 있다.
- 재현하지 못하는 것: 카드 창이 없던 구간의 프레임(저장하지 않음), 스캐너가 카드 창을 늦게(링 범위 2초보다 늦게) 알린 구간의 앞부분, OS 캡처 시계, 당시 PC의 처리 속도, 기록기가 버린 프레임(메모에 읽음·저장·버림 수와 프레임당 변환·전송 시간이 남는다).
- 재실행 충실도: 재실행이 기록된 간격을 지키지 못하면(프레임의 99% 미만 전달, 최대 지연 250ms 초과, 33ms 초과 지연 5% 초과) 영상 파이프라인이 프레임을 합쳐 결과가 달라진다. 이런 실행은 이력에 "지연 큼"으로 표시하고 비교에서 경고한다. 측정 사례: 같은 PC에서 다른 부하가 있으면 지연이 평균 수백 ms~수 초가 되었고 읽은 장수가 크게 줄었다.
- 프레임 간격이 불규칙한 구간은 기록기 탓이 아니라 입력 자체의 특성이다. 실제 공유 기록(304프레임)에서 150ms가 넘는 간격 18곳은 받은 시각의 간격과 캡처 타임스탬프의 간격이 거의 같았다(예: 316 대 316ms). 즉 브라우저가 그 시간 동안 새 프레임을 주지 않았다. 원인(화면 변화 기반 캡처인지, 스캐너 부하로 캡처가 느려졌는지)은 구분하지 못했다.
- 같은 입력 판정: 파일 해시가 같고 알려져 있을 때만 같은 입력으로 인정한다.
- 기록을 켠 실행과 끈 실행의 판독 결과는 합쳐 비교하지 않는다.

## 검증 현황

- 무손실: RGBA·I420·NV12 쓴 바이트와 읽은 바이트가 같다(테스트).
- 서버: 순서 뒤바뀐 업로드의 순번 정렬, 중복·과거 순번 거부, 유휴 자동 봉인, 고아 기록 복구, 동시 봉인, 코덱 변환(`scripts/transcode-recording.mjs`)을 테스트로 확인했다.
- 실측: 영상 재생 기록은 읽은 프레임의 98.5%를, 사용자의 실제 화면 공유(2560×1440 I420, 90초)는 2171프레임 중 2171프레임(누락 0)을 저장했다. 크기는 UtVideo 기준 90초에 약 4.5GB.
- 재실행 전달: 서버 디코딩 스트림은 UtVideo 기록 기준 초당 약 65프레임(기록 24fps의 2.7배).

## 사용

- 개발 서버에서 평소처럼 화면 공유 후 스캔하면 자동으로 쌓인다(`?rec=0`인 개발 검사 페이지는 제외).
- `/dev/recording.html`에서 기록을 고르면 재실행하고 결과를 기록 옆에 저장한다. 같은 기록의 두 실행을 골라 카드 단위로 비교한다.
- 용량: 카드 창이 잡힌 프레임만 저장하므로 실제 공유 90초 기록은 41프레임(약 수십~수백 MB)이다. 이전 방식의 전체 기록은 분당 약 3GB였다. 카드 창을 계속 띄워 두고 오래 공유하면 그만큼 쌓이므로 디스크를 확인한다.

## 배포본(v0.2.0)과 작업 트리 비교 (2026-11-11)

같은 기록을 두 빌드로 순차 재실행하고 카드 단위로 비교한다: `node scripts/compare-recording-runs.mjs` (`--json` 지원). 기준선은 요약의 빌드 이름이 `HEAD`로 시작하는 실행, 나머지는 현재 빌드다. 기준선 실행은 배포 커밋을 별도 worktree로 열고 이 저장소의 기록 도구(`recording-store/server/runs`, `recorded-share-frames`)를 복사한 뒤 순차 재실행 페이지로 돌려 같은 `/__rec` 서버에 저장한다(기록·실행 파일은 `fixtures/local/recordings`).

기록 8개(전체 프레임 2개, 라이브 기록 6개)의 결과 — 인식은 거의 같고 남은 차이는 아래뿐이다:

| 차이 | 기록 | 해석 |
|---|---|---|
| 가르가디스·베스칼·바실리오의 추가 장수: 기준선 `0`, 현재 `null`(미판독) | 3개(카드 4건) | 현재 쪽이 "장수 실패를 0으로 바꾸지 않는다"를 지키는 방향. 실제 값은 사람이 확인해야 한다 |
| 도철을 다루는 웨이: 기준선 장수 `null`, 현재 `0` | 1개 | 현재 쪽 개선(원인은 아래 "남은 차이: 도철을 다루는 웨이") |
| 읽음 수: 현재가 1 많음(41c5) / 1 적음 | 41c5 등 | 위 차이의 결과 |

- 정답(사람이 확인한 값)이 없어서 어느 쪽이 맞는지는 판정하지 않는다. 위는 "다른 곳"의 목록이다.
- `미확인` 수는 두 빌드가 다르게 센다(현재는 인식 필요 관측을 따로 둔다). 비교 지표로 쓰지 않는다.
- 이 비교는 기록 8개의 순차 재실행에 한정된다.

### 해결한 차이: 드렉탈라스가 현재 빌드에서만 빠짐

- 증상: 기록 2개(983b, 3d98)에서 기준선은 드렉탈라스를 읽고 현재 빌드는 "원화 후보 마진 부족 · 재촬영 필요"로 폐기했다. 카드는 가림 없이 온전했다(이름 또렷, 장수 `+1`).
- 원인(재실행 보고서의 `unresolved`, 원화 매처 진단): 글자 인식이 `드렉탈란스`(한 글자 오인식, 신뢰도 91.9, 이름 점수 .93, 격차 .40)로 읽혔고, 글자와 함께 원화를 맞추는 경로(상관 ≥.93, 격차 ≥.3)는 이 카드를 **승인**했다(상관 .9328, 격차 .546). 그런데 `fuseIdentity`가 그 승인된 근거에 글자 없이 쓰는 엄격한 기준(상관 ≥.94)을 다시 적용해 `weak-artwork`로 뒤집었다. v0.2.0은 승인된 근거를 그대로 확정했다.
- 수정: 호출부(`recognizer.ts`)가 `artworkAccepted`를 넘겨, 매처가 이미 승인한 원화 근거에는 엄격 기준을 다시 적용하지 않는다. 글자 없이 원화만 쓰는 경우(엄격 기준)와 이름·원화 충돌은 그대로 미확정이다. 회귀 테스트는 `tests/identity-fusion.test.ts`.
- 검증: 수정 후 8개 기록을 모두 다시 돌려 두 기록에서 카드 목록이 기준선과 같아졌고(드렉탈라스 각성 0·장수 1), 다른 기록에 새 차이는 생기지 않았다. 이는 v0.2.0 동작을 회복한 것이며 기준을 새로 느슨하게 한 것이 아니다.
- 남은 점검: 글자 동반 기준(상관 .93)이 충분히 엄격한지는 이 기록들만으로 판단하지 않는다.

### 남은 차이: 가르가디스·베스칼·바실리오의 추가 장수 (기준선 `0`, 현재 `null`)

- 저장 이미지로 확인한 사실: 세 카드 모두 온전하고, 왼쪽 아래에 빈 칸만 있으며 `+N` 카드 아이콘이 없다(0장으로 보인다).
- 현재 빌드가 `null`로 두는 이유(재실행 보고서의 `countReview`와 `count-pattern.ts`의 `packCount` 진단을 같은 이미지로 계산):
  1. 카운터 영역에 아이콘 색·숫자 획·아이콘 잔상이 없지만 **아이콘 자리가 평평**(`iconFlat`)해서 `flatCover`로 판정되고 `hasIcon`이 `null`(판단 불가)이 된다. 평평한 불투명 조각(예: 툴팁)이 아이콘과 숫자를 함께 가릴 수 있어 한 장면만으로는 "없음"과 "가려짐"을 구분하지 못하게 한 안전장치다.
  2. 저장 이미지 재확인(`recheckStablePreviewFields`)은 같은 증거(`stablePreviewEmptyCandidate`, 세 카드 모두 참)를 **관측 3번 이상**일 때만 `0`으로 인정한다. 이 기록들에서 세 카드는 1~2번만 관측됐다.
- 확인: 같은 세 카드가 983b에서는 7·6·3번 관측되어 현재 빌드도 `0`으로 읽는다. 95개의 `0` 카드 중 관측 3번 미만이 7개인 것은 고정 0·회색 표식 등 다른 증거 경로로 확정됐을 가능성이 있다(어느 경로인지는 확인하지 않았다).
- 결론: 현재 빌드의 `null`은 규칙대로이고(장수 실패를 0으로 바꾸지 않음), v0.2.0의 `0`은 이 이미지들에서 맞아 보이지만 증명 없이 확정한 값이다. 어느 쪽을 택할지는 정책 결정이며, 판독 불가 카드는 "확인 필요"로 안내된다. 이 판단은 카드 3장의 이미지에 한정된다.
- 재실행 보고서에 카드별 관측 횟수(`observations`)를 추가했다. 값이 같더라도 증거의 강도를 볼 수 있다.

### 남은 차이: 도철을 다루는 웨이 (기준선 장수 `null`, 현재 `0`) — 현재 쪽 개선

- 기록 ac03에서만 나온 차이다. 저장 이미지와 원본 프레임(4.24초)에서 카드는 가림 없이 온전하고 `+N` 표시가 없다(빈 보석 5칸). 값은 `0`이 맞다. 이름이 두 줄로 꺾이는 긴 이름이다.
- 기준선(v0.2.0): 이 카드를 2번 관측했고, 판독에 쓴 관측(4.24초)의 카운터 영역을 "가림 또는 불명확"(`hasIcon null`)으로 판정했다. OCR 여러 개가 근거를 못 내 `unconfirmed`로 끝났고 저장된 다른 관측은 다시 보지 않았다.
- 현재: 같은 카드를 6번 관측했고, 마무리 단계 저장 이미지 재확인(`recheckStablePreviewFields`, 최대 8개 관측 이미지)에서 명시적 빈 카운터(`hasIcon false`, 숫자 획·아이콘 없음)를 찾아 `0`을 확정했다. 저장된 관측 이미지 3개가 모두 같은 판정이었다.
- 즉 현재 쪽 이득은 "한 관측이 애매하면 다른 저장 관측으로 다시 확인한다"는 기존 설계(`GOAL.md`의 다중 preview 재판독)이며, 새 규칙(관측 1번 0 반영)과는 무관하다. 4.24초 관측이 왜 애매했는지(첫 화면 전환 직후 흔들림 등)는 확인하지 못했다. 가림은 아니었다.

#### 규칙 조정: "관측 3번 이상" 요건 → 관측 1번부터 (2026-11-11 적용·확정, `docs/decisions.md`)

## 기록 상태 표시와 조용한 실패 (2026-11-11)

- 증상: 스캔은 정상으로 도는데 서버에 기록이 전혀 생기지 않은 세션이 있었다(시작 실패를 `catch`로 삼켜 이유를 알 수 없었다).
- 이제 스캔 중 기록 상태가 **브라우저 탭 제목**에 보인다: `●REC 저장된/읽은 프레임f`(진행), `⚠REC 실패(...)`·`⚠REC 시작 안 됨(...)`(문제), 끝나면 `✓REC N프레임 저장` 또는 `⚠REC 저장된 프레임 없음`. 시작 실패와 프레임 버림의 첫 이유는 콘솔(`[share-recorder]`)에도 남고, 봉인 메모에는 버린 이유별 개수가 들어간다.
- 기록 시작 전에 창 크기가 바뀌면(공유 직후 창이 아직 크기를 바꾸는 중) 이전에는 첫 프레임의 크기에 고정되어 이후 모든 프레임이 "크기가 달라서" 조용히 버려졌다. 이제 서버에 크기를 알리기 전이면 새 크기로 다시 시작한다(알린 뒤의 크기 변경은 그대로 버리고 센다). 이것이 위 증상의 원인인지는 확인하지 못했다.

## 라이브 스캔 결과도 서버에 저장 (2026-11-11)

- 개발 서버에서 화면 공유 스캔을 하면, 그 스캔의 최종 결과(카드 목록·읽은 장수·미확인 수)를 기록 옆의 `runs/run-live.json` 한 파일에 저장한다(`live-run-report.ts`). 재실행 보고서와 같은 형식이라 재실행 페이지에서 "라이브(스캔 당시 결과)" 행으로 나타나고, 재실행과 카드 단위로 비교할 수 있다.
- 스캔 중에는 약 1초에 한 번(마지막 상태만) 같은 파일을 덮어쓴다(`PUT /__rec/<id>/runs/live`). 그래서 새로고침이나 비정상 종료 뒤에도 마지막 상태가 남는다. 기록이 봉인되면 해시가 담긴 최종 보고서(`live.final: true`)를 한 번 더 쓴다.
- 일반 HTTP를 쓴다(웹소켓 불필요). 개발 서버가 같은 오리진이라 별도 포트·설정이 없다. 실패는 모두 무시해 스캔에 영향을 주지 않는다.
- 개발 전용이다: `import.meta.env.DEV` 분기 안의 동적 import만 사용하므로 배포 번들에 들어가지 않는다(`npm run build` 후 `dist`에서 `__rec`, `share-recorder`, `run-live` 등 0건 확인).
- 라이브와 재실행의 숫자가 한두 장 어긋날 수 있다. 라이브는 실제 시간에 맞춰 프레임을 처리하고 판독 대기열 순서가 달라지지만, 재실행은 프레임을 한 장씩 순서대로 넣기 때문이다(예: 라이브 378장 대 재실행 377장). 재실행끼리의 결과는 매번 같다.

## 재실행 방식과 검증 결과 (2026-11-10)

- **순차(기본)**: 서버 기록의 모든 프레임을 기록된 시각과 함께 스캐너의 기존 전체 프레임 순차 입력에 공급한다(`dev/recorded-share-frames.ts`). 기계 부하와 무관하고 프레임당 약 80ms다. 처리 압력은 재현하지 않는다.
- **실시간 간격(옵션)**: `MediaStreamTrackGenerator`로 기록된 간격대로 내보낸다(`dev/recorded-share-input.ts`). 스캐너가 메인 스레드를 쓰는 동안 프레임 공급이 같이 밀려 프레임이 합쳐지므로 결과가 부하에 좌우된다(같은 기록에서 79~288장). 충실도 기준(프레임 99% 전달, 최대 지연 250ms, 33ms 초과 5% 이하)에 못 미치면 "불충실"로 표시하고 비교에서 경고한다.
- **시도했다가 쓰지 않은 방식**: (1) 프레임이 스캐너에 표시된 것을 확인하고 다음 프레임을 내보내는 보조 속도 — 프레임당 약 0.6초로 90초 기록에 20분 이상 걸리고 스캐너가 원래 건너뛰던 프레임까지 처리한다. (2) 워커의 OffscreenCanvas 캡처 — 프레임의 약 21%가 캡처에서 빠진다. 워커에서의 `VideoTrackGenerator`는 이 브라우저에 없다.

검증:
- 같은 실제 화면 공유 기록(2160프레임대, I420 2560×1440)을 순차로 3번 재실행: 288장 읽음, 카드 290개, 차이 0.
- 배포본(v0.2.0 커밋)과 개발 작업 트리를 같은 기록으로 순차 재실행해 비교:
  - 실제 공유 기록: 카드 288장 동일. 가르가디스·베스칼의 추가 장수만 다름(배포본 0장, 개발 미판독). 개발 쪽이 "장수 실패를 0으로 바꾸지 않는다" 불변 조건을 지키는 방향의 차이로 보이며, 실제 값은 사람이 확인해야 한다.
  - video-3 영상 기반 기록(541프레임): 카드 354장 전부 동일.
- 한계: 이 비교는 순차 판독이다. 라이브 경로(프레임 선택·지연), 개발 서버 부하, 화면 안내 차이는 이 도구로 비교하지 못했다. 기록은 2개뿐이라 일반화하지 않는다.
