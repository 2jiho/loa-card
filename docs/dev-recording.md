# 개발용 화면 공유 기록·재실행

개발·테스트 전용이다. 개발 서버에서 화면 공유로 스캔하면 **스캐너가 카드 창(격자)을 잡은 구간(앞뒤 2초 포함)의 프레임을 전부 로컬 서버에 바로 저장**하고, 저장된 기록을 같은 입력으로 다시 실행해 코드 버전별 결과를 비교한다. 카드 창이 없는 시간(다른 창, 대기)은 저장하지 않는다. 배포 앱에는 포함하지 않는다(`vite serve` 전용 플러그인, `import.meta.env.DEV` 분기). 보안은 범위 밖이다(로컬 개발 전용).

재실행 명령과 매개변수는 [개발과 검증](development.md#스캔-재실행-검사), 기록·재현·비교의 계약은 [입력 기록과 재현 설계](scanner-session-design.md), 스캔의 동작은 [스캐너 구조](scanner-pipeline.md)를 따른다.

기록 자체와 기록을 근거로 한 날짜별 조사·측정 메모는 Git에 넣지 않는다. 메모는 비공개 기록 옆의 `fixtures/local/notes/`에 둔다(Git·배포 제외). 그 기록이 없는 곳에서는 메모의 수치를 다시 확인할 수 없으므로 현재 동작의 근거로 쓰지 않는다.

## 목표와 비목표

- 새로고침·브라우저 저장소 초기화·탭 종료와 무관하게 공유 중 받은 프레임이 서버 디스크에 남는다.
- 브라우저 메모리·저장소 한도에 묶이지 않는다. 용량은 서버 디스크가 정한다.
- 기록은 판독을 기다리게 하거나 늦추지 않는다. 기록기가 뒤처지면 프레임을 버리고 그 개수를 기록에 남긴다.
- 재실행은 서버가 프레임을 디코딩해 흘려 주므로 브라우저 메모리를 쓰지 않는다.
- 비목표: 보안, 배포 앱의 기록, 이전 `.loareplay` 호환.

## 저장 형식

`fixtures/local/recordings/<id>/` (Git 제외 영역)

| 파일 | 내용 |
|---|---|
| `meta.json` | id, 시작 시각, 크기, `pixelFormat`, `colorSpace`, `codec`, 상태(`open`/`sealed`), 프레임 수, 완전성, 파일 해시, 메모, 환경 |
| `frames.mkv` | 저장한 모든 프레임. 무손실. 프레임 번호 = 순번 |
| `frames.jsonl` | 프레임마다 한 줄: `seq`, `mediaTimeMs`, `deliveredAtMs`(세션 시작 기준), `receivedAtMs` |
| `run-live.json` | 공유 중 앱의 실제 결과(재실행 보고서와 같은 형식) |
| `runs/run-*.json` | 이 기록의 재실행 보고서(요약 + 카드 목록) |

- `frames.jsonl`이 시각의 기준이다. mkv의 pts는 쓰지 않는다.
- 픽셀 형식: 공유 영상의 **원본 YUV**(`i420`/`nv12`)를 변환 없이 저장한다(프레임당 1.5바이트/픽셀). 원본 레이아웃을 알 수 없는 프레임은 `rgba`로 대체한다. NV12는 정확한 재배열로 I420로 보관한다.
- 코덱: 원본 YUV는 x264 무손실(`-preset ultrafast -qp 0`, `meta.codec: h264-lossless`)로 저장한다. 스크롤하는 목록은 이웃 프레임이 거의 같아 프레임 내 압축보다 훨씬 작다. `ultrafast`는 B프레임·선행 탐색이 없어 비정상 종료한 기록도 마지막 프레임까지 디코딩된다. RGBA 대체 형식은 Ut Video다. 이전의 FFV1·Ut Video YUV 기록도 그대로 읽힌다. 선택 근거는 `dev/recording-store.ts`의 머리 설명에 있다.
- 기존 기록의 코덱 변환: `scripts/transcode-recording.mjs`.

## 흐름

1. 개발 서버에서 화면 공유 스캔(`runScanner`, `source==='screen'`)이 시작되면 기록기(`reproduction/share-recorder.ts`)가 공유 영상 트랙을 복제해 `MediaStreamTrackProcessor`를 만들고, 그 프레임 스트림을 워커(`reproduction/share-recorder-worker.ts`)로 넘긴다. 프레임은 워커가 직접 읽으므로 스캐너가 메인 스레드를 바쁘게 써도 기록이 굶지 않는다.
2. 워커는 프레임마다 `VideoFrame.copyTo`로 원본 바이트를 복사해 메모리 링(최대 320MB, 시간 제한 없음)에 둔다. 해상도·픽셀 형식·프레임률에 따라 링에 2초 분량이 다 들어가지 않을 수 있다. 스캐너가 카드 창을 찾을 때마다 기록기에 신호를 주면, 워커는 링의 최근 2초와 이후 2초의 프레임을 `PUT /__rec/<id>/start`, 이어서 프레임마다 `POST /__rec/<id>/frame`(원시 바이트 + 시각·순번 헤더, 최대 8개 동시)으로 올린다. 서버는 순번대로 쓴다(`x-seq`). 카드 창과 먼 프레임은 링에서 밀려나 저장되지 않는다.
3. 서버(`dev/recording-server.ts`, `dev/recording-store.ts`)가 ffmpeg(`ffmpeg-static`)에 프레임을 흘려 쓰고 `frames.jsonl`에 줄을 더한다.
4. 종료 시 `POST /__rec/<id>/seal`. 카드 창이 있는 구간만 프레임이 오므로 조용한 시간이 길 수 있어, 10분 동안 프레임이 없을 때만 서버가 자동 봉인한다(페이지 종료·크래시). 봉인되지 않은 채 남은 기록(서버 재시작 등)은 `POST /seal`로 복구한다: 실제 디코딩되는 프레임만 인정하고 `complete:false`로 표시한다.
5. 재실행(`/dev/recording.html`): `GET /__rec/<id>/frames`가 ffmpeg 출력을 그대로 흘려 주고, 브라우저가 프레임을 조립해 `VideoFrame`으로 만들어 `MediaStreamTrackGenerator`에 기록된 간격대로 쓴다. 스캐너는 진짜 공유와 같은 `MediaStream` 트랙을 받는다. 색 정보(primaries/matrix/range)도 함께 복원한다.

## 정직한 범위

- 재현하는 것: 카드 창이 보인 구간(앞뒤 2초 포함)에서 기록기가 받은 모든 프레임의 픽셀(원본 YUV, 아니면 RGBA), 순서, 간격. 스캐너가 처리했는지와 무관하므로 스캐너가 빨라져 더 많은 프레임을 처리해도 같은 기록으로 시험할 수 있다.
- 재현하지 못하는 것: 카드 창이 없던 구간의 프레임(저장하지 않음), 스캐너가 카드 창을 링 범위보다 늦게 알린 구간의 앞부분, OS 캡처 시계, 당시 PC의 처리 속도, 기록기가 버린 프레임(메모에 읽음·저장·버림 수와 프레임당 변환·전송 시간이 남는다).
- 재실행 충실도: 재실행이 기록된 간격을 지키지 못하면(프레임의 99% 미만 전달, 최대 지연 250ms 초과, 33ms 초과 지연 5% 초과, `dev/recording-runs.ts`) 영상 파이프라인이 프레임을 합쳐 결과가 달라진다. 이런 실행은 이력에 "지연 큼"으로 표시하고 비교에서 경고한다. 같은 PC에서 다른 부하가 있으면 지연이 커지고 읽은 장수가 줄 수 있다.
- 프레임 간격이 불규칙한 구간은 기록기가 아니라 입력 자체의 특성일 수 있다. 받은 시각의 간격과 캡처 타임스탬프의 간격이 같으면 브라우저가 그 시간 동안 새 프레임을 주지 않은 것이다. 그 원인(화면 변화 기반 캡처인지, 스캐너 부하로 캡처가 느려졌는지)은 기록만으로 구분하지 못한다.
- 같은 입력 판정: 파일 해시가 같고 알려져 있을 때만 같은 입력으로 인정한다.
- 기록을 켠 실행과 끈 실행의 판독 결과는 합쳐 비교하지 않는다.

## 테스트로 확인하는 것

- 무손실: RGBA·I420·NV12의 쓴 바이트와 읽은 바이트가 같다.
- 서버: 순서 뒤바뀐 업로드의 순번 정렬, 중복·과거 순번 거부, 유휴 자동 봉인, 고아 기록 복구, 동시 봉인, 코덱 변환.

실제 공유에서 저장률·용량·재실행 전달 속도는 PC와 입력에 따라 다르므로 기록마다 `meta.json`의 메모와 재실행 보고서로 확인한다.

## 사용

- 개발 서버에서 평소처럼 화면 공유 후 스캔하면 자동으로 쌓인다(`?rec=0`인 개발 검사 페이지는 제외). 기록 중에는 탭 제목에 읽음·저장 프레임 수와 실패가 보이고(`reproduction/recording-indicator.ts`, 페이지 자체는 바꾸지 않는다), 기록이 실패하거나 누락돼도 스캔은 계속되며 meta의 note에 남는다.
- 카드 창을 찾지 못하는 화면도 남긴다(개발 서버 전용): 입력 크기로 맞춘 배율(`inputScale`)이 기록으로 확인한 배율(`orchestration/scanner.ts`의 `TESTED_SCALES`)이 아니거나, 공유 후 5초 안에 창을 못 찾으면 공유 전체를 기록한다. `?record=all`이면 항상 전체를 기록한다.
- `/dev/recording.html`에서 기록을 고르면 재실행하고 결과를 기록 옆에 저장한다. 같은 기록의 두 실행을 골라 카드 단위로 비교한다. 명령줄은 `scripts/run-recording-replay.mjs`, 비교는 `scripts/compare-recording-runs.mjs`.
- 용량: 카드 창이 잡힌 프레임만 저장하지만, 카드 창을 계속 띄워 두고 오래 공유하면 그만큼 쌓이므로 디스크를 확인한다.
- 스캔 순서를 바꾼 파생 기록: `scripts/derive-recording.mjs`(명령은 [개발과 검증](development.md#스캔-재실행-검사)). 원본 프레임을 다른 순서로 이어 붙인 비공개 파생 기록이며 실제 공유가 아니다(meta의 note에 출처를 적는다). 원본은 바꾸지 않는다. 같은 프레임을 다른 순서로 보낼 뿐이라 스크롤 관성·가속은 실제와 다르다.

## 진행 창 자동 점검

진행 창(목록 지도·확정 수·행동 안내)의 문제를 사람이 실제 공유로 하나씩 찾지 않도록, 기록 재실행에서 창이 보여 준 상태를 남기고 자동으로 검사한다.

- 기록: `rowlive` 재실행 보고서의 `monitorTimeline`. 스캔 상태가 나갈 때마다(공유 중 약 0.2초) 앱과 같은 투영(`rowScannerState` → `projectScanMonitorState` → `monitorAction`)으로 지도·안내·수치와 창 전체 상태를 적는다(`dev/monitor-timeline.ts`). 그림은 넣지 않는다.
- 동작 검사: `node scripts/check-monitor-timeline.mjs <id> [run]`. 실패하면 종료 코드 1.
  1. 화면 상자가 지나간 카드 줄(가운데 두 줄)이 모두 다 읽은 줄(또는 다시 볼 줄)로 칠해지는가. 상자는 도착한 프레임을 따라가고 칠은 그 프레임을 읽은 뒤라, 둘 사이 시간(판독 지연)은 적기만 하고 판정하지 않는다(움직이는 스크롤바는 한 줄 앞설 수 있어 가장자리 줄은 멈추거나 가운데에 오면 칠한다)
  2. 다 읽은 줄이 아무 표시 없이 되돌아가지 않는가(헤더를 읽어 빈칸·잠긴 칸이 된 줄은 제외)
  3. 강조가 2초 안에 꺼졌다 다시 켜지지 않는가
  4. 행동 안내가 2초 안에 A→B→A로 바뀌지 않는가, 창 찾기가 잠깐씩 끊기지 않는가
  5. 빈칸·잠긴 칸 구간과 목록 크기가 바뀌지 않는가, 화면 상자가 튀었다 돌아오지 않는가(스크롤바 오독)
  6. 모든 카드가 확정된 뒤에는 다시 볼 줄도 "넘겨 주세요"도 없는가, 확정 수가 줄지 않는가
  7. 완료면 강조 없이 카드 줄이 모두 초록인가, 미완료면 어디를 볼지 표시하는가
- 배치 검사(브라우저): `/dev/monitor-timeline.html?id=<id>&run=<run>&width=<px>`가 기록된 상태를 앱의 `ScanMonitorPanel`로 차례로 그려 각 부분의 위치·높이 변화와 넘침을 `window.__monitorLayout`에 남긴다. `&at=<번호>`는 그 상태 하나를 그린다(스크린샷용). 280·340(진행 창)·600px에서 본다. `&fill=1`은 별도 진행 창처럼 창 크기의 프레임에서 패널이 창을 채우는 배치(`fill`)로 그린다.
- 한계: 재실행은 이 PC의 처리 속도와 기록의 입력에 따른다. 실제 공유의 손 움직임·게임 부하·브라우저 창 크기는 재현하지 않는다. 파생 기록은 실제로 아래에서 위로 넘긴 공유가 아니다.
