- 상태: 제안 (승인 대기)
- 작성일: 2026-11-08
- 관련 문서: `GOAL.md`, `docs/scanner-pipeline.md`, `docs/scanner-session-design.md`, `docs/field-proof-gaps.md`
- 코드 기준: `src/features/card-scanner/scanner.ts` (264KB), `name-reader.ts`, `portrait-matcher.ts`, `visual-fields.ts`, `detector.ts`

## 1. 배경과 문제

현재 스캐너는 video-1~7과 screenshots-1·2에서 수량·이름·필드를 상당히 읽는다. 그러나 다음 이유로 **새 카드·새 해상도·실제 화면 공유에서 같은 성능을 보장하지 못한다.**

1. **평가가 코퍼스 수량 중심이다.** `unresolved 0`은 “다 읽었다”가 아니라 “못 읽은 관측을 `discardedObservations`로 옮겼다”는 뜻이다. video-1의 62건, video-2의 5건, video-3의 66건+1칸이 그렇다.
2. **판독 불가와 인식 실패가 같은 버킷이다.** 사람이 읽을 수 있는 관측도 엔진이 실패하면 `인식 필요`로 버려진다. 이 둘을 분리하지 않으면 “가려진 것만 제외”라는 완료 기준을 검증할 수 없다.
3. **기하가 2560×1440에 고정되어 있다.** `detector.ts`의 10열×4행, 140×210 내부 좌표, 고정 필드 마스크는 다른 해상도·UI 배율에서 재보정이 필요하다.
4. **이름 OCR 단독 의존 구간이 남아 있다.** 합성 420장에서 417장 중 415장 정확, 장문 골드 이름 2장 실패, 28장 부분 문자열 모호다. 원화 특징은 있지만 이름 후보와의 융합이 1급 경로가 아니다.
5. **카탈로그 갱신이 수동이다.** 새 패치 카드가 카탈로그에 없으면 이름·원화 사전에 없으므로 인식할 수 없다. “모르는 카드”를 억지로 맞추지 않고 `카탈로그 미등록`으로 남기는 경로도 없다.
6. **live 복구가 finalization의 discard에 가깝다.** 공유 중 “이 카드를 다시 보여 주세요”라고 요구해 읽을 수 있는 관측을 회수하는 루프가 아니라, 종료 후 남은 관측을 버리는 패치다.
7. **실제 화면 공유 E2E가 미검증이다.** 긍정 완료 영수증·CSV·2분 자동 중지·커서·다른 해상도가 실제 Chrome/Edge 공유에서 확인되지 않았다.

## 2. 목표와 완료 기준

### 2.1 전체 목표

모든 테스트 입력에서 **사람이 읽을 수 있는 카드의 이름·각성(0~5)·추가 장수(0~15)를 정확히 확인**한다. 사람이 읽을 수 없는 카드(툴팁·커서 가림, 카드 뒷면, 완전한 저대비·블러, 화면 밖)는 값을 추정하지 않고 `인식 필요`로 남긴다.

### 2.2 필드별 판독 가능성

한 카드의 이름이 보여도 장수가 가려질 수 있으므로 판독 가능성을 **필드별**로 나눈다.

| 구분 | 정의 |
|---|---|
| `nameReadable` | 사람이 입력의 최소 한 프레임에서 전체 이름을 읽을 수 있음 |
| `awakeningReadable` | 사람이 최소 한 프레임에서 각성 0~5를 읽을 수 있음 |
| `copiesReadable` | 사람이 최소 한 프레임에서 추가 장수 0~15를 읽을 수 있음 |
| `unreadable` | 해당 필드가 모든 프레임에서 가려졌거나 판독 불가 |

분모는 필드별 `readable`만 센다. `unreadable`은 분모에서 제외하되 **사유와 증거 프레임을 별도 목록으로 남긴다.**

### 2.3 완료 게이트

다음을 모두 만족할 때만 “완료”로 본다.

1. **읽을 수 있는 카드의 이름 100% 정확** — `identified / nameReadable = 100%`
2. **읽을 수 있는 각성·장수 100% 정확** — 필드별 `exact / readable = 100%`
3. **오확정 0** — 엔진이 확정한 값이 사람 라벨과 다른 경우가 0. 이는 커버리지보다 우선한다.
4. **읽을 수 있는데 놓친 관측 0** — `readableButMissed = 0`. `인식 필요`에는 `unreadable`만 남는다.
5. **수량 일치** — `cards = expected`, 필드별 완료 수 = `expected - unreadable`.
6. **review 0** — 읽을 수 있는 카드에 `review`가 남지 않는다.
7. **실제 화면 공유** — 긍정 완료 영수증, CSV, 2분 자동 중지, 커서 제외가 실제 Chrome/Edge 공유에서 확인된다.
8. **다른 해상도·UI 배율** — 최소 1개 이상의 2560×1440 외 입력에서 같은 게이트를 통과한다.
9. **회귀** — 기존 `npm test`, lint, build가 통과하고, 새 평가셋에서 이전 기준선 대비 악화가 없다.

### 2.4 비목표

- 가려진 카드의 값을 추정해 100%로 만들지 않는다.
- 수량 일치만으로 완료를 선언하지 않는다.
- 테스트 영상에 맞춘 임계값·예외 카드 목록을 추가하지 않는다.
- `unresolved 0`을 인식 100%로 표현하지 않는다.

## 3. 핵심 원칙

1. **사람 라벨이 유일한 정답이다.** 프로그램 출력, 이전 버전 결과, 수량 일치는 정답이 아니다.
2. **읽을 수 있음/없음은 사람이 판정한다.** 엔진 실패를 “원래 못 읽는 카드”로 승격하지 않는다.
3. **필드별로 판정한다.** 이름은 읽혔지만 장수가 가려진 경우를 이름 실패로 세지 않는다.
4. **오확정 0이 커버리지보다 우선한다.** 불확실하면 `null` 또는 `인식 필요`다.
5. **`null`과 관측된 0을 구분한다.** 0은 아이콘 부재·숫자 획 부재의 명시적 근거가 있을 때만 확정한다.
6. **최신 기준은 캡처 시각이다.** 처리 완료 시각이 아니다.
7. **정확한 전체 이름만 확정한다.** 부분 문자열은 경쟁자이며 자동 병합하지 않는다.
8. **원화 단독 일치는 정답이 아니다.** 이름·등급·원화·차순위 격차를 함께 본다.
9. **같은 프레임의 여러 크롭은 독립 반복이 아니다.** 캐시·재시도도 독립 관측이 아니다.
10. **카탈로그에 없으면 `카탈로그 미등록`이다.** 가장 비슷한 카드로 억지 매칭하지 않는다.
11. **평가셋은 튜닝에 쓰지 않는다.** 학습·튜닝셋과 홀드아웃 평가셋을 분리한다.
12. **기존 live 입력·기록·재현 구조는 재사용한다.** 전체 앱을 갈아엎지 않는다.

## 4. 목표 흐름 (입력 → 완료)

### 4.1 세션 시작

- 사용자가 창 공유를 선택한다. `displaySurface: "window"` 우선.
- 세션은 입력 소스, 해상도, UI 배율, 브라우저, 시작 시각, 카탈로그 버전을 기록한다.
- 카탈로그·모델 버전이 맞지 않으면 스캔을 시작하지 않거나 `카탈로그 미등록` 경고를 먼저 표시한다.

### 4.2 기하 정규화

- 매 프레임이 아니라 창·그리드가 바뀌었을 때 다음을 검출한다.
  - 카드 창의 위치·크기·배율
  - 10열 기준 열 간격·행 간격
  - 카드 내부 140×210 정규화 좌표
  - 성장 탭·헤더·스크롤바 앵커
- 고정 2560×1440 상수를 기본값이 아닌 “알려진 레이아웃 중 하나”로 취급한다.
- 검출 실패·불확실 시 카드 크롭을 확정하지 않는다.
- 테두리 4변 연속성·가림 검사를 통과한 크롭만 관측으로 만든다.

### 4.3 관측과 증거 원장

각 관측은 다음을 가진다.

| 증거 | 내용 |
|---|---|
| 신원 | 이름 OCR 후보(전체 문자열·신뢰도·격차), 원화 top-k와 마진, 등급 색상, 슬롯/스크롤 위치 |
| 각성 | 5개 보석 슬롯의 금색/회색 비율, 형태, 관측 시각 |
| 장수 | 1~15 패턴 점수·차순위, 숫자 OCR 보조, 아이콘/숫자 부재 증거 |
| 품질 | 테두리 정렬, 가림 플래그, 블러·저대비, 프레임 안정성, 캡처 순서 |
| 출처 | 물리 프레임 ID, 캡처 시각, 슬롯, 그룹, 입력 모드 |

- 관측은 카드별 원장에 캡처 시각 순서로 쌓는다.
- 같은 물리 프레임의 크롭·캐시 재사용·동일 프레임 재시도는 독립 관측으로 세지 않는다.
- 원장은 “카드 ID가 확정됐다”와 “필드가 확정됐다”를 별도로 기록한다.

### 4.4 신원 해석 (이름 + 원화 융합)

1. 카탈로그에서 이름 후보를 만든다.
   - 정확 일치, 정규화 일치, 편집 거리, 부분 문자열 경쟁자.
2. 원화 후보를 만든다.
   - 24×32 특징, 상단/하단 영역, 등급·장착 배너 제외.
   - top-k와 1위-2위 마진을 유지한다.
3. 후보를 융합한다.
   - 이름 정확 일치 + 원화 일치 → 확정.
   - 이름 모호 + 원화가 경쟁자를 명확히 분리 → 확정 검토.
   - 원화만 일치 + 이름 근거 없음 → 확정하지 않음.
   - 이름·원화가 충돌 → `인식 필요`.
4. 카탈로그에 어떤 후보도 임계값을 넘지 못하면 `카탈로그 미등록`으로 남긴다.
   - 이 경우에도 억지로 기존 카드에 매칭하지 않는다.
5. 장문·골드 이름은 다음 순서로 보완한다.
   - 다중 크롭·다중 전처리 OCR
   - 원화 top-k와 이름 후보 겹침
   - 두 독립 프레임의 동일 이름
   - 그래도 불확실하면 `인식 필요`

### 4.5 필드 해석 (각성·장수)

- 각성: 5개 보석 슬롯의 금색 비율·형태로 0~5. 5각과 양수 장수의 규칙 충돌 시 각성을 미확인으로 둔다.
- 장수: 1~15 전체 패턴, 숫자 OCR 보조, 차순위 격차. 0은 아이콘 부재와 숫자 획 부재를 모두 확인할 때만 확정한다.
- 각성별 상한 `15 - a(a+1)/2`를 검증에 사용하되, 상한에 맞추려고 값을 선택하지 않는다.
- 필드 충돌은 캡처 시각 기준 최신 관측으로 해소한다. 해소되지 않으면 `review`.
- 같은 카드의 여러 관측이 같은 값을 독립적으로 지지하면 신뢰를 올린다. 단, 같은 프레임·캐시·재시도는 제외한다.

### 4.6 live 복구와 사용자 안내

- 공유 중 카드별 “읽을 수 있는 증거가 아직 없는 필드”를 추적한다.
- 다음 경우 특정 카드/필드를 다시 보여 달라는 안내를 표시한다.
  - 이름은 읽혔지만 각성·장수가 불확실
  - 이름이 모호하고 원화 마진이 부족
  - 테두리·가림으로 크롭이 거부됨
- 안내는 “전체를 다시 스캔”이 아니라 **해당 카드만 다시 노출**하도록 구체적으로 표시한다.
- 자동 종료는 읽을 수 있는 필드의 증거가 남아 있으면 보류한다.
- 공유 종료 후에도 회수하지 못한 관측만 `인식 필요`로 남긴다.
- `인식 필요` 사유는 `가림`, `카드 뒷면`, `저대비·블러`, `화면 밖`, `카탈로그 미등록`으로 구분한다.

### 4.7 최종 정산

- `expected`(보관함 수량)와 카드 목록을 대조한다.
- 카드가 가득 찼거나, pinned `인식 필요` 슬롯을 포함해 `expected`와 맞으면 최종 중복 분류를 허용한다.
- 중복 분류는 진단용이며 카드 값 확정 근거가 아니다.
- 완료 영수증은 다음을 모두 만족할 때만 발행한다.
  - 읽을 수 있는 이름·각성·장수 100%
  - 오확정 0
  - `readableButMissed 0`
  - 입력 근거 손실 0
  - 최종 헤더·최신 필드·입력 종료 조건 충족
- CSV·백업·리포트는 `인식 필요` 목록과 사유를 함께 저장한다.

### 4.8 평가와 보고

- 모든 실행은 다음 표를 자동 생성한다.

| 입력 | expected | nameReadable | nameExact | awakeningReadable | awakeningExact | copiesReadable | copiesExact | readableButMissed | unreadable | falseConfirm | review |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|

- `unreadable`은 사유별로 나눈다.
- 수량 일치와 판독 커버리지를 같은 열에 섞지 않는다.
- 리포트에는 코드 버전·카탈로그 버전·모델 버전·해상도·브라우저·입력 해시를 남긴다.

## 5. 책임 경계와 모듈

`scanner.ts`는 오케스트레이션만 유지하고, 인식 판단을 다음 모듈로 분리한다.

| 모듈 | 책임 | 하지 않는 일 |
|---|---|---|
| `layout-normalizer.ts` (신규) | 창·그리드·배율·카드 정규화 좌표 검출 | 카드 신원·필드 확정 |
| `identity-evidence.ts` (신규) | 이름 후보·원화 후보·등급 근거 수집 | 후보 융합 확정 |
| `identity-resolution.ts` (신규) | 후보 융합, 마진, `카탈로그 미등록` 판정 | 픽셀 획득·UI |
| `field-evidence.ts` (신규) | 각성·장수 근거 수집 | 최신값 병합 |
| `observation-ledger.ts` (신규) | 카드별 증거·캡처 순서·충돌·미확정 상태 | OCR 실행 |
| `acquisition-guidance.ts` (신규) | live 재노출 안내·필요 증거 계산 | 값 추정 |
| `completion.ts` / `negative-completion.ts` | 완료 영수증·부정 사유 | 인식 |
| `scanner.ts` | 입력·큐·스케줄·기존 상태 연결 | 인식 알고리즘 세부 |

기존 `name-reader.ts`, `portrait-matcher.ts`, `count-pattern.ts`, `star-pattern.ts`, `detector.ts`는 유지하되, 새 모듈 뒤에서 호출한다. 한 번에 전부 교체하지 않는다.

| screenshots-1·2, 개별 사진 | 사진 입력 회귀 | 기존 라벨 유지 |
| 합성 420장 | 새 카드 이름 일반화 | `work/composed-card-templates/equipped/` |
| 해상도·배율 변형 | 기하 일반화 프록시 | 실제 캡처가 아님을 명시 |
| 새 화면 공유 기록 | live E2E | 사용자 제공 필요 |
| 새 패치 카드 | 카탈로그 일반화 | 클라이언트 데이터 갱신 필요 |

### 6.2 라벨링

- 이름·수량의 1차 진실은 게임 보관함 목록과 기존 사람 라벨이다.
- 각성·장수는 가장 선명한 프레임에서 사람이 필드별로 라벨링한다.
- 각 관측에 `nameReadable`·`awakeningReadable`·`copiesReadable`과 근거 프레임을 기록한다.
- 기존 `work/human-label-*.json`을 형식에 맞게 이관한다.
- 라벨 파일은 해시와 출처를 남기고, 프로그램 출력을 자동 승격하지 않는다.
- 라벨이 없는 카드는 “정답”으로 세지 않는다. 먼저 라벨을 만든다.

### 6.3 게이트

- **오확정 0**: 어떤 입력에서도 사람 라벨과 다른 확정 값이 없어야 한다.
- **읽을 수 있는 필드 100%**: 분모는 필드별 `readable`.
- **읽을 수 있는데 놓친 관측 0**: `readableButMissed`.
- **회귀 없음**: 기존 테스트와 이전 평가셋 대비 악화 없음.
- **live E2E**: 실제 공유에서 영수증·CSV·자동 중지·커서.
- **다른 해상도**: 최소 1개 외부 입력에서 게이트 통과.

## 7. 단계별 실행 계획

각 단계는 앞 단계의 게이트를 통과한 뒤 진행한다. 단계별로 커밋하지 않고, 사용자 요청 시에만 커밋한다.

### Phase A — 기준선과 정답셋

1. 현재 코퍼스 전체를 평가 러너로 실행하는 기준선을 만든다.
2. `readable`/`unreadable` 필드 라벨을 만든다.
3. `readableButMissed`, `falseConfirm`, `unreadable` 사유를 분리해 리포트한다.
4. 기존 `discardedObservations`를 “읽을 수 있었는지” 기준으로 재분류한다.

**종료 기준:** 모든 현재 입력에 대해 필드별 분모·분자·오확정이 재현 가능하게 보고된다. 코드 인식 변경은 하지 않는다.

### Phase B — 기하 정규화

1. `layout-normalizer`로 창·그리드·배율 검출을 분리한다.
2. 1080p/1440p/4K 및 UI 배율 변형 프레임으로 좌표·크롭을 검증한다.
3. 고정 2560×1440 상수를 “알려진 레이아웃”으로 격하한다.
4. 테두리·가림 검사는 새 좌표에서 다시 검증한다.

**종료 기준:** 변형 입력에서 카드 크롭이 사람이 확인 가능한 수준으로 일치하고, 기존 코퍼스 결과가 악화되지 않는다.

### Phase C — 신원 융합

1. `identity-evidence`와 `identity-resolution`을 도입한다.
2. 이름 후보 + 원화 top-k + 등급 색상을 융합한다.
3. 장문·골드 이름 2장(3201017, 3202044)을 해결한다.
4. 부분 문자열 모호 28장을 원화·추가 프레임으로 분리한다.
5. `카탈로그 미등록` 경로를 추가한다.
6. 합성 420장과 코퍼스 이름 라벨로 평가한다.

**종료 기준:** 합성 숫자 ID 417/417 정확(3장은 display-only로 제외), 코퍼스 `nameExact/nameReadable = 100%`, 오확정 0. `카탈로그 미등록`은 별도로 표시된다.

### Phase D — 필드 판독

1. `field-evidence`로 각성·장수 근거를 분리한다.
2. 다중 관측 병합을 캡처 시각 기준으로 통일한다.
3. 0장 확정 근거를 강화하고, 읽을 수 있는 0을 `null`로 두지 않는다.
4. 베스칼 장수 리뷰를 사람 라벨과 대조해 해결한다.
5. 코퍼스의 `awakeningExact`·`copiesExact`를 필드별로 평가한다.

**종료 기준:** 읽을 수 있는 각성·장수 100%, 오확정 0, 읽을 수 있는 카드의 review 0.

### Phase E — live 복구·완료

1. `acquisition-guidance`로 카드별 부족 증거를 계산한다.
2. 공유 중 특정 카드 재노출 안내를 연결한다.
3. 자동 종료는 읽을 수 있는 필드 증거가 남으면 보류한다.
4. 최종 정산에서 `readableButMissed`와 `unreadable`을 분리한다.
5. 실제 Chrome/Edge 공유에서 영수증·CSV·2분 자동 중지·커서를 확인한다.

**종료 기준:** 실제 공유에서 읽을 수 있는 카드 전부 판독, `인식 필요`는 `unreadable`만, 긍정 영수증 발행, CSV·자동 중지·커서 확인.

### Phase F — 일반화·성능·문서

1. 새 패치 카드 카탈로그 갱신 절차를 검증한다.
2. 다른 해상도·UI 배율 입력을 추가 검증한다.
3. 성능·메모리·기록 비용을 측정한다.
4. `GOAL.md`, `docs/scanner-pipeline.md`, `docs/field-proof-gaps.md`를 새 기준으로 갱신한다.
5. `CHANGELOG.md`는 릴리스 시에만 갱신한다.

**종료 기준:** 전체 게이트 통과, 문서·재현 명령·남은 한계가 일치한다.

## 8. 데이터·카탈로그 갱신

- 새 패치 카드: 클라이언트 데이터 → `scripts/build-client-data.py` → `public/scanner/cards.json`·`stars.json` → 합성 템플릿·평가셋 → 회귀.
- 카탈로그 버전을 실행 리포트에 기록한다.
- 카탈로그에 없는 카드는 `카탈로그 미등록`으로 남기고, 다음 갱신 대상 목록에 넣는다.
- 공개 fixture와 비공개 코퍼스를 섞지 않는다.
- 외부 자산 고지·해시·버전을 함께 갱신한다.

## 9. 위험과 미해결 질문

### 위험

- **라벨링 비용**: 모든 카드의 필드별 판독 가능성을 사람이 확인해야 한다. 자동화할 수 없는 부분이다.
- **실제 해상도 입력 부재**: 합성 스케일 변형은 실제 UI 배율·폰트 렌더링을 대신하지 못한다.
- **게임 패치**: 카탈로그·원화·UI가 바뀌면 재검증이 필요하다.
- **성능**: 증거 원장·융합이 스캔 속도와 메모리를 늘릴 수 있다. 기존 10초 목표와 충돌하지 않게 단계별로 측정한다.
- **기존 코드 결합**: `scanner.ts`가 커서 분리 중 회귀가 날 수 있다. 모듈 경계를 한 번에 넓히지 않는다.

### 미해결 질문

1. “읽을 수 있음”을 이름·각성·장수 필드별로 나누는 판정에 동의하는가?
2. 다른 해상도·UI 배율 입력을 언제 제공할 수 있는가? 제공 전까지 합성 변형을 프록시로만 인정하는가?
3. 실제 화면 공유 E2E를 Phase E에서 사용자가 직접 1회 제공할 수 있는가?
4. 합성 420장 중 템플릿이 없는 display-only 3장은 평가 분모에서 제외하는가?
5. 새 패치 카드 카탈로그는 어떤 주기로 갱신할 것인가?
